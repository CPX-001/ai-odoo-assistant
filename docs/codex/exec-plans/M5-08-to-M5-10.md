## Invariantes

- Browser -> Odoo -> Assistant Service; el browser no llama directamente al service.
- Identidad, compañías, ACL, record rules y acceso a campos se derivan y validan en Odoo bajo el usuario efectivo.
- El Assistant Service no ejecuta SQL contra la DB productiva de Odoo.
- No `sudo()`, shell/SQL/Python libres ni ejecución genérica de métodos como tools.
- Schemas Odoo efectivos son datos runtime; `application` no contiene branches por major.
- Source/log/knowledge sólo leen roots/providers resueltos y validados.
- `FULLY_READY` conserva el significado aprobado: service, Assistant DB, Codex, source y LogProvider operativos, con scan válido.
- M5 es estrictamente read-only: sin writes, previews, approvals ni business actions.
- Codex es un adapter sustituible; policy, schemas, budgets, tools y evidencia los gobierna software determinista.

## Decisiones

- El panel usará selección explícita de workflow enviada como hint y validada server-side contra una allowlist antes de preparar delegación o llamar al Assistant Service.
- Cada workflow conserva su endpoint y registry mínimo dentro del Assistant Service; no existe una unión de tools.
- Las capabilities M5 serán diagnósticas y sanitizadas; no se añadirán a la fórmula histórica de readiness global.
- Una gate que requiera infraestructura externa no se declarará PASS con mocks. Si implementación y tests deterministas son verdes pero falta auth/runtime compatible, se documentará `CONDITIONAL`.

## Descubrimientos

- El repo ya contiene workflows QUERY y HOW_TO, adapters dinámicos, knowledge FTS y metadata de navegación; M5-08 es integración/routing/hardening, no una reimplementación.
- El Source of Truth no autoriza ampliar `FULLY_READY` con query/navigation/knowledge/how_to.
- El E2E M5 real terminó PASS: QUERY A=2/B=1; HOW_TO citó navegación/schema/documento; stale y runtime ausente degradaron seguro.
- PostgreSQL 16 requiere membership explícita antes de crear una DB owned por un rol recién creado desde una identidad CREATEROLE no-superuser.
- PostgreSQL FTS con `plainto_tsquery` aplica AND; el tool indica consultas cortas y reintento lexical para evitar candidatos vacíos por sobreespecificación.

## Riesgos

- El E2E real depende de Odoo 18, Chromium, PostgreSQL y un runtime Codex autenticado en el host de gate.
- La UI debe representar cuatro tipos nuevos de citas sin convertir Markdown/HTML adversarial en DOM ejecutable.
- Los negativos de staleness, record rules y cleanup deben demostrarse en el runner, no inferirse desde mocks.

## Criterio de cierre

M5 sólo queda cerrado con el veredicto permitido por M5-10, documentación consistente, verificaciones relevantes ejecutadas, árbol limpio y cambios committeados y enviados a `origin/main`.
