# ExecPlan — cierre M6 contra el Source of Truth

## Objetivo

Implementar secuencialmente M6-11, M6-12 y M6-13 para cerrar el scope
`record_patch` + `record_create` + una business action real curada, conservando
el boundary obligatorio `proposal -> preview -> approval -> commit ->
verification` y todas las invariantes de seguridad existentes.

## Estado inicial

- `main` sincronizado en `86f9aaf` y sin cambios locales.
- M6-01..M6-10 implementados; suite y E2E real previos verdes.
- `docs/M6_GATE_REPORT.md` permanece en FAIL únicamente porque faltan create
  seguro y una business action curada exigidos por el Source of Truth.
- No existe ADR ni actualización del Source of Truth que reduzca ese alcance.

## Decisiones

- Reutilizar contratos, persistencia de proposals, approval state machine,
  authorities `a1`, verification y audit; no construir un segundo sistema.
- Implementar primero un único `record_create` bounded e idempotente ante
  respuesta perdida, y verificarlo antes de tocar la business action.
- Implementar como primera acción curada `sale.order.confirm.v1` mediante un
  handler Odoo explícito; no aceptar model/method/context arbitrarios.
- Mantener Codex limitado a schema/preview y el browser a `proposal_id` más
  decisión; commit y payload autoritativo siguen siendo host-controlled.

## Descubrimientos

- El checkout inicial estaba en `58c9d76`; `git pull --ff-only` incorporó los
  packets M6-11..13 y dejó `main` en `86f9aaf`.
- El gate técnico previo ya incluye Odoo 18 + Assistant PostgreSQL + Codex +
  Chromium; la ampliación debe extender ese runner, no sustituirlo por mocks.
- La registry ACTION debe estrecharse por intención de turno; las instrucciones
  del reasoning engine también deben describir la familia real seleccionada.
- Las líneas de venta del fixture deben ser cotizaciones válidas con producto;
  así `action_confirm()` prueba la regla de negocio real, no un método simulado.

## Riesgos

- Create y confirmación de pedido requieren receipts Odoo-side que distingan
  retry del mismo attempt de una operación externa para no duplicar efectos.
- La representación común de previews debe ampliarse sin romper la UX ni los
  contratos de `record_patch` ya desplegados.
- El E2E real depende de runtimes externos ya usados por M6-09; si dejan de
  estar disponibles, M6-13 no podrá declarar PASS.

## Acceptance criteria

- M6-11 y M6-12 cumplen íntegramente sus task packets y verificaciones.
- Create y business action no duplican efectos tras respuesta perdida.
- `record_patch` y M1-M5 no regresan.
- M6-13 emite un veredicto basado en evidencia real y sólo marca PASS si todos
  los checks del Source of Truth están verdes.
