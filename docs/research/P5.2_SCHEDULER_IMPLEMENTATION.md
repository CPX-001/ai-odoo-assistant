```text

```

## Implemented contract

### Capacity and race-safe admission

`odoo_ai_assistant.concurrent_turns` is the administrator-facing installation ceiling. The current physical pool remains two `ir.cron` slots, so the effective supported range is 1..2 and invalid direct parameter edits are safely clamped.

Claims use a short PostgreSQL advisory transaction lock. A real scheduler claim cursor explicitly uses `READ COMMITTED` before acquiring that lock. Odoo's normal production cursors use `REPEATABLE READ`; without the local isolation change, a worker waiting on the advisory lock could retain a stale snapshot and still observe capacity from before the previous claim committed.

Odoo's `TransactionCase` replaces new registry cursors with a shared `TestCursor` whose transaction is already active and whose cursor access is serialized by the test framework. That cursor cannot legally change transaction isolation after prior test queries. The claim helper therefore leaves `TestCursor` isolation untouched; true multi-connection admission races are acceptance-owned by the real two-cron/browser gates rather than being falsely claimed from the transaction test harness.

The lock covers only:

```text
capacity read
-> eligibility/fairness selection
-> queued -> running + lease transition
-> commit
```

Provider and business execution never hold the scheduler lock.

### Conversation causality

A queued candidate is ineligible while an older turn in the same conversation is:

```text
queued and still retryable
running
cancel_requested
awaiting_confirmation
```

Ordering uses durable turn identity (`id`) rather than `queued_at`, because retries may intentionally move `queued_at` forward.

`completed`, `failed`, `cancelled` and `recovery_required` are terminal for scheduling. `recovery_required` remains a user-visible recovery obligation but is never replayed automatically and does not permanently freeze later conversation turns.

### Fairness

Every successful claim updates `scheduler_claimed_at`. Candidate ranking is:

```text
fewest active turns for that user
-> least recently claimed user
-> oldest eligible queued_at
-> turn id
```

This is intentionally small rather than a general queue framework. It provides the required behavior:

- one user may use spare slots when nobody else waits;
- a zero-active waiting user gets capacity before another backlog turn from a user already active;
- with capacity=1, service rotates toward the least recently served waiting user instead of falling back to permanent global FIFO starvation;
- retry/requeue updates the service watermark on every new claim and therefore does not regain unfair priority merely because its queue timestamp is old.

### Release wake-up

After a claimed worker returns, the scheduler triggers another bounded claim attempt. The next claim rechecks capacity and causality, so the wake-up is safe after completion, terminal failure, cancellation, recovery transition or pause for approval.

Queued cancellation and approval/rejection can release a causal predecessor outside a worker transaction. Those paths register a post-commit wake callback so another worker cannot observe the successor before the authoritative state change commits.

Odoo transaction tests do not execute post-commit hooks like production cursors do, so the deterministic suite verifies registration and callback behavior separately rather than depending on `TestCursor.commit()` to execute the hook.

Wake-up failure is logged but cannot rewrite an already authoritative business/turn result; the periodic cron remains a recovery fallback.

### Operational visibility

Administrator diagnostics now expose aggregate scheduler facts only:

```text
configured/effective/supported capacity
active count / available slots
queued / eligible / causally blocked counts
awaiting-confirmation count
queued and active user counts
oldest queue wait seconds
```

No prompt text, answers, tool arguments/results, provider-private data or chain-of-thought are included.
