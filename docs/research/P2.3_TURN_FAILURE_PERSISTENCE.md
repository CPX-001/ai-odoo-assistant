## Objective

Persist the validated Phase 2 `FailureEnvelope` on terminal Odoo turns and project it through
`browser_status()` while preserving the existing `error_code` compatibility field. The durable
queue `write_barrier` remains the authority for whether a business effect may have happened.

## Prerequisites

- P2.1 `FailureEnvelope`: complete.
- P2.2 provider normalization: complete.
- Phase 1 provider/tool/cancellation real-environment gates: complete.
- No unresolved prerequisite validation debt blocked implementation.

## Implementation

Added `runtime/agent/terminal_failure.py` as the host terminal projection layer. It consumes either
an already validated carried provider envelope or a sanitized terminal `error_code`, then applies
queue-owned effect authority:

```text
write_barrier = false -> effect_state = none
write_barrier = true  -> effect_state = unknown
                         retryability = never
                         user_action = review
```

The barrier rule is intentionally conservative. Provider retry hints never override uncertainty
after effectful execution has become possible.

Added `models/turn_failure.py` as an Odoo model extension:

- adds nullable readonly `failure_payload` JSON to `odoo.ai.turn`;
- validates explicit payloads with `parse_failure_envelope()` before persistence;
- creates a bounded fallback envelope for generic terminal `failed` / `recovery_required` writes;
- clears stale failure payloads when a turn is requeued;
- returns `failure` from `browser_status()` while keeping `error_code` unchanged;
- preserves the original queue failure/retry path for non-provider errors;
- only uses a specialized finalizer when the caught exception already carries a validated provider
  `FailureEnvelope`, so P2.2 provider category/status/code facts survive atomically into the terminal
  turn.

The existing stale-worker recovery function is unchanged. Its terminal writes pass through the new
model `write()` overlay, so `worker_lost` and `worker_lost_after_write_barrier` now receive bounded
failure envelopes without duplicating the stale-recovery state machine.

Addon version was advanced from `18.0.10.7.0` to `18.0.10.8.0` because the Odoo model gains a new
stored field and therefore requires a module update on an existing database.

## Preserved invariants

- Odoo remains persistence and operational authority.
- Effective-user capability execution and `su=False` are unchanged.
- The existing queue retry discriminator remains `error_code`; P2.3 does not change retry policy.
- No automatic provider, capability or write retry was added.
- `write_barrier` / `recovery_required` remain the no-blind-retry authority.
- Provider message text, stdout/stderr, prompts, credentials and unrestricted payloads are not
  persisted.
- Browser projection re-validates the stored envelope and fails closed to `failure = null` if the
  stored shape is invalid or does not match the legacy `error_code`.
- Frontend prose and retry controls are unchanged in this slice.

## Odoo 18 validation

`addons/odoo_ai_assistant/tests/test_turn_failure.py` now covers:

- carried provider category/status/provider code persisted on terminal failure;
- `browser_status().failure` plus legacy `error_code` parity;
- write-barrier override to `effect_state=unknown`, `retryability=never`, `user_action=review`;
- bounded generic ACL fallback envelope.

The first real focused run found that a later event-sequence update could overwrite a carried
provider envelope with a generic fallback. The `write()` overlay was repaired so fallback synthesis
runs only for an explicit terminal/error transition or when no failure payload exists. This keeps
later unrelated writes from destroying the original provider facts.
