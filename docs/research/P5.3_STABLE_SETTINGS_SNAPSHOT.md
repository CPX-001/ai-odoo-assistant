## Objective

Make the settings that determine one persisted Assistant turn explicit and immutable after enqueue. A user may change model/autonomy selectors while another turn is unresolved, but those changes affect only later turns.

P5.1 already persisted `reasoning_model` and `policy_payload`, and its browser validation demonstrated the essential A/B behavior. P5.3 therefore formalizes and hardens that existing boundary instead of introducing another settings registry or another runtime configuration path.

## Small implementation slices

### P5.3a — versioned host-owned snapshot

`b46b72e9db077f4a9e661800cad82f4aba51121f`

Adds `odoo.ai.turn.execution_settings_payload`, derived host-side when a normal persisted turn is created. Callers cannot supply a competing snapshot payload.

Snapshot format v1 contains:

```text
format_version
reasoning_model
autonomy_profile
policy
```

The policy is the already resolved per-turn policy payload. Its existing validator remains the policy schema authority; P5.3 does not duplicate policy precedence.

Once a turn has this snapshot, writes to `reasoning_model`, `policy_payload` or `execution_settings_payload` are rejected. Approval/rejection may still transition and resume the same turn because the existing approval path requeues that persisted turn rather than creating a replacement turn.

### P5.3f — formal real product-path harness

`41808dc01349773d1d583e48b33a44c27efeca5c` -> `00a818806c4de7206bd30bff6ec7c0ac8d7c5d4e`

Adds a dedicated Playwright runner plus machine-readable gate contract for `P5-REAL-SETTINGS-SNAPSHOT`. The runner uses the same real Odoo Assistant UI interaction pattern previously accepted in P5.1, but now validates the P5.3 versioned payload itself:

- Turn A is created under model/profile A and remains unresolved;
- its `reasoning_model`, `policy_payload` and `execution_settings_payload` agree;
- UI model/autonomy changes do not mutate A's complete v1 snapshot;
- Turn B captures model/profile B in a new v1 snapshot;

The browser fixture is deliberately read-only. Approval same-turn retention remains covered by P5.3e rather than creating a business mutation solely for this browser gate.

## What is frozen vs revalidated dynamically

Frozen for the turn:

```text
selected reasoning model
user autonomy profile represented by the captured user policy layer
resolved policy layers and turn limits
```

Deliberately **not** frozen:

```text
user active state
current company membership
ACL / record rules / field access
capability availability and dynamic guards
provider/runtime operational availability
```

A stale snapshot must never preserve permission that Odoo has since revoked. This keeps P5.3 aligned with the existing host-authority and `su=False` invariants.

There is no separate current technical-profile selector to invent for this slice. If a future profile becomes an execution input, the snapshot contract should be versioned deliberately rather than adding a placeholder today.

## Failure modes covered by the design

- UI preference change mutates Turn A: blocked by persisted immutable snapshot.
- Approval resumes with current UI policy instead of Turn A policy: existing runtime continues to consume Turn A's stored policy/model.
- Caller supplies a forged parallel snapshot: ignored; snapshot is derived by the host from resolved turn values.
- Revoked Odoo access remains usable because it was snapshotted: avoided; authorization is still checked at execution time.
- Historical/direct test turns without a normal policy snapshot: tolerated; the invariant applies to normal newly enqueued product turns and avoids breaking historical fixtures unnecessarily.
