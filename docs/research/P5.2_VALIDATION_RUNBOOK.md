# P5.2 scheduler validation runbook

Date: 2026-08-28  
Status: executable batched validation handoff; **not PASS evidence**

This runbook intentionally validates P5.2a + P5.2b + P5.2c together after implementation, rather than requiring a real-environment stop between the internal sub-slices.

## Acceptance target

P5.2 may become COMPLETE only when one tested lineage demonstrates all of the following:

```text
bounded installation capacity
race-safe claims / no double claim
parallel independent conversations
one active causal turn per conversation
awaiting approval blocks only its conversation
anti-starvation fairness across users
retry/requeue does not regain unfair priority
capacity release wakes pending work promptly
write-barrier/recovery semantics remain intact
scheduler diagnostics are bounded/admin-only
P5.1 multichat behavior has not regressed
```

## 1. Pull and identify exact lineage

Use current `main`, record the exact SHA, update/install the addon on the disposable Odoo 18 validation database and do not reuse acceptance evidence from an older checkpoint.

The database used by browser/provider gates must remain disposable and should follow the existing `odoo_ai_*` naming convention.

## 2. Static / contract preflight

Run the repository's normal syntax/XML checks plus:

```text
python tests/e2e/p5_2_real_gate_check.py
node --check tests/e2e/p5_2_scheduler_browser.mjs
```

These checks only validate harness/contract shape; they are not real gate PASS.

## 3. Focused Odoo scheduler tests

Run the addon tests containing at least:

```text
TestAssistantTurnScheduler
TestAssistantTurnSchedulerFairness
TestAssistantTurnQueue
TestAssistantTurnFailurePersistence
```

The focused scheduler/fairness tests must all pass before accepting the real scheduler behavior.

Pay particular attention to the truly concurrent cursor/thread cases. A serialized-looking test that never overlaps claim attempts is not a substitute.

## 4. Full addon regression

If focused tests pass, run the complete `/odoo_ai_assistant` Odoo battery.

Also rerun the relevant P5.1 browser regression for multichat/reopen if the real gate batch or any repair touches frontend turn ownership.

Do not record skipped or unavailable tests as PASS.

## 5. Real environment gates

Environment expected by the P5.2 browser runner:

```text
ODOO_AI_P5_BASE_URL
ODOO_AI_P5_DB
ODOO_AI_P5_LOGIN
ODOO_AI_P5_PASSWORD
```

The login must be a disposable **system administrator** test user because the gate temporarily changes the scheduler capacity and reads admin-only aggregate diagnostics.

Run:

```text
node tests/e2e/p5_2_scheduler_browser.mjs --gate P5-REAL-MULTICHAT
node tests/e2e/p5_2_scheduler_browser.mjs --gate P5-REAL-CONVERSATION-ORDERING
node tests/e2e/p5_2_scheduler_browser.mjs --gate P5-REAL-BACKPRESSURE
```

### P5-REAL-MULTICHAT

With effective capacity 2, two long read-only turns in independent conversations must overlap in `running` state. Diagnostics must never show more than two active turns.

### P5-REAL-CONVERSATION-ORDERING

With capacity available, a later turn in the same conversation must remain `queued` while its predecessor is active. After the predecessor reaches a terminal state, the successor must become eligible without being manually resubmitted.

### P5-REAL-BACKPRESSURE

With effective capacity 1, a second independent turn must remain durably `queued`, not fail. After the capacity holder is released, the waiting turn must leave `queued` promptly rather than relying on the one-minute periodic cron as normal behavior.

The runner emits `OBSERVED_OK_NOT_AUTOMATIC_PASS`. Review the observed states/measurements before recording formal PASS.

## 6. Evidence to record

Sanitized P5.2 evidence should include:

```text
tested SHA
Odoo/PostgreSQL/Python/Codex/Playwright/Chromium versions
configured + effective capacity
focused Odoo test totals
full addon test totals
peak simultaneous active turns
queued/eligible/blocked observations
wake delay after capacity release
no-double-claim result
fairness result
P5.1 regression result
three real gate results
```

Do not store credentials, cookies, Codex authentication material, raw provider payloads, hidden reasoning or business-sensitive prompts/results.

## 7. Failure handling

If any P5.2 deterministic or real gate fails:

- keep P5.2 active;
- classify the smallest owning layer (capacity/claim, causality, fairness, wake-up, diagnostics or harness);
- repair that layer;
- rerun the affected focused tests and relevant real gate;
- rerun the full addon battery when scheduler runtime code changed.

Do not weaken a concurrency assertion merely to obtain green output.

## 8. Exit

Only after all required P5.2 deterministic/regression/real gates pass on one coherent lineage:

```text
P5.2 -> COMPLETE
P5.3 -> READY
```

Until then P5.3 remains blocked by the P5.2 HARD concurrency/ordering contract.
