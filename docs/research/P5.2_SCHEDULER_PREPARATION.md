# P5.2 scheduler concurrency and backpressure preparation

Date: 2026-08-28  
Inspected `main`: `b763774b08b243d97ea35c7f5b74e16334113ff0`  
Status: **REVIEWED PREPARATION — P5.2 READY, not implemented**

This record was prepared before P5.1 acceptance and reviewed after P5.1 passed on the repaired
frontend lineage. It defines the next eligible scheduler slice, but does not claim any P5.2 gate PASS
and deliberately makes no runtime change.

The active roadmap rule remains:

```text
P5.1 accepted
  -> P5.2 may become eligible
```

## 1. Problem to solve

The current durable queue already supports independent background turns, but concurrency is an
implementation side effect of two fixed `ir.cron` records rather than an explicit product policy.
P5.2 must turn that into a bounded host-owned scheduler contract while preserving all current
lease, cancellation, retry, write-barrier and recovery semantics.

Initial causal rule from the Phase 5 playbook:

```text
one active causal turn per conversation
multiple conversations may run concurrently
```

When execution capacity is exhausted, turns remain durably `queued`; normal Odoo and Assistant UI
must remain usable.

## 2. Current queue baseline observed in code

Current `addons/odoo_ai_assistant/models/turn_queue.py` provides:

- durable `queued` turns before provider execution;
- two native cron runner records;
- one turn claimed per cron invocation;
- `FOR UPDATE SKIP LOCKED` candidate claiming;
- FIFO ordering by `queued_at, id`;
- a per-turn lease token and five-minute lease expiry;
- bounded attempts;
- cancellation and stale-worker recovery;
- post-write-barrier recovery protection;
- requeue after retryable pre-barrier failure;
- server-side execution under the originating effective user with `su=False`.

Both cron records are triggered on enqueue. Recovery/requeue also retriggers the two records.
Normal completion and transition to approval currently do not explicitly wake another queued turn;
remaining work may therefore depend on already-pending cron triggers or the periodic cron interval.

## 3. Gaps visible before implementation

### 3.1 No explicit installation-wide capacity ceiling

There is no host configuration such as `max concurrent Assistant turns`. The practical ceiling is
currently derived from two cron records plus Odoo's available cron workers.

That is not sufficient as a product contract because deployment capacity, provider limits and Odoo
worker capacity can differ.

### 3.2 Same-conversation causal serialization is not enforced by claim selection

`_claim_next_turn()` currently chooses the oldest queued row regardless of conversation. With two
workers, two queued turns belonging to the same conversation can therefore be claimed independently.
That conflicts with the Phase 5 initial ordering rule.

The future claim predicate must make only the oldest eligible queued turn in a conversation
claimable and must not start it while that conversation has an active causal predecessor.

At minimum `running`, `cancel_requested` and `awaiting_confirmation` must be considered when defining
the causal blocker contract. `recovery_required` needs explicit product semantics rather than being
silently treated as worker capacity: it is terminal from the worker perspective but still carries a
user-visible recovery obligation.

### 3.3 No explicit fairness rule

Global FIFO is simple, but one user can place a large older backlog ahead of another user's newly
queued interactive work. P5.2 requires bounded anti-starvation behavior without preventing one user
from using spare capacity when nobody else is waiting.

### 3.4 Capacity release does not have one canonical wake-up path

A slot becomes free after completion, failure, cancellation, recovery transition or provider work
pausing for approval. The scheduler should wake pending eligible work at those release points rather
than relying on the one-minute periodic cron as normal backpressure behavior.

### 3.5 No scheduler observability contract

The durable state exposes `queued/running/...`, but the host does not yet expose bounded scheduler
facts such as effective capacity, active count, eligible queue depth or queue wait age for diagnostics
and acceptance evidence.

These facts must remain host-known operational telemetry, not model authority.

## 4. Reference pattern reviewed

OCA `queue_job` 18.0 is useful as a pattern reference because it has configurable channel capacity,
parallel independent jobs, PostgreSQL-backed jobs, retries and stale-job recovery. Its documentation
also shows deployment capacity being configured separately from individual jobs.

What is useful here:

```text
bounded named capacity
queued work waits instead of failing
parallel independent work
explicit retry/recovery behavior
capacity as deployment configuration
```

What should not be copied by default:

```text
new queue framework dependency
replacement of current odoo.ai.turn persistence
second authority path for retries/effects
job-runner architecture solely because OCA uses it
```

The current native queue already owns turn identity, write-barrier recovery and user authority, so
P5.2 should first extend it. Replacing it with `queue_job` would require an ADR and evidence that the
replacement materially improves the product.

## 5. Preferred minimal direction to evaluate once P5.2 is eligible

### 5.1 Keep `odoo.ai.turn` as the durable queue item

Do not introduce another job record as turn authority. Existing turn states, leases and recovery
remain canonical.

### 5.2 Add a small host-owned capacity policy

The effective execution limit should be bounded and resolved host-side from configuration and
runtime constraints. Conceptually:

```text
effective_turn_capacity = min(
    configured_installation_ceiling,
    supported_runner_capacity,
    provider_ceiling_when_known,
)
```

The first implementation does not need a general provider framework merely to support Codex. It
should leave a clean seam for a future provider-specific ceiling instead of hard-coding provider
logic throughout the queue.

A native Odoo setting/config parameter is preferred for the installation ceiling. The default can
remain equivalent to today's effective behavior until measurement justifies another default.

### 5.3 Make claim decisions race-safe without serializing execution

A configured global ceiling cannot be enforced by `COUNT(running)` alone if two cron workers can
perform that check concurrently. The claim-control decision needs a short database coordination
mechanism.

A promising minimal option is a transaction-scoped PostgreSQL advisory lock around only the
capacity/eligibility selection and state transition:

```text
acquire short scheduler claim lock
 -> recover/count current active capacity
 -> choose one eligible queued candidate
 -> mark candidate running + lease
commit/release claim lock
 -> execute turn without scheduler lock
```

This would serialize only the tiny claim decision, not provider work or business transactions. It
must be tested against Odoo connection behavior before adoption. A dedicated semaphore model is an
alternative if advisory locking proves awkward; Python threads/custom dispatchers are not preferred.

### 5.4 Enforce one active causal turn per conversation in SQL eligibility

Candidate selection should satisfy both:

```text
candidate is the oldest queued turn for its conversation
AND no active causal predecessor blocks that conversation
```

This must be enforced in the host claim path, not merely by disabling a browser composer. Future
surfaces such as automation/MCP must inherit the same ordering rule.

### 5.5 Prefer work from users with less active capacity, then FIFO

A simple fairness target to evaluate:

```text
lowest current active-turn count for the user
 -> oldest eligible queued_at
 -> id
```

With the claim decision serialized, this allows a single user to consume spare slots when alone but
lets another user with zero active turns overtake additional backlog from a user already consuming
capacity.

If deterministic concurrency tests show this is insufficient, add the smallest explicit per-user
fairness state rather than immediately building a general queue scheduler.

### 5.6 Wake the queue whenever capacity is released

Normal release paths should schedule another bounded claim attempt after their transaction reaches a
safe state. This includes at least:

```text
completed
failed
cancelled
recovery_required
awaiting_confirmation (worker capacity released, causal conversation remains blocked)
```

Wake-up must never happen before an effect/recovery transaction reaches its authoritative state.

## 6. Configuration shape to keep small

The first P5.2 implementation should avoid a matrix of tuning knobs. A minimal administrator-facing
setting is preferable:

```text
Assistant concurrent turns: N
```

Advanced/provider-specific limits can remain technical configuration until there is evidence that
administrators need them independently.

The UI should explain that actual throughput may also be lower because of Odoo cron workers,
provider limits or machine resources. Increasing the setting must never create more authority; it
only affects scheduling capacity.

## 7. Required deterministic coverage once implementation starts

Do not add these as passing tests before the runtime behavior exists. The P5.2 implementation slice
should create focused Odoo tests using independent cursors where race behavior matters.

### Capacity

```text
limit=1 + two simultaneous claim attempts -> exactly one running turn
limit>=2 + two independent conversations -> both may be running
over capacity -> excess remains queued, not failed
capacity release -> pending eligible turn is woken/claimed
```

### Conversation ordering

```text
two queued turns same conversation -> only oldest can claim
older turn running -> later same-conversation turn remains queued
older turn awaiting confirmation -> later same-conversation turn remains queued
terminal predecessor -> next turn becomes eligible
```

### Double-claim/recovery

```text
concurrent claim attempts never return the same turn
lease ownership remains mandatory
stale pre-barrier worker still requeues within bounded attempts
stale post-barrier worker still enters recovery and is never blindly replayed
```

### Fairness

```text
user A backlog + user B waiting + free slot -> B eventually receives capacity
one user only -> spare capacity is not artificially left idle
retry/requeue does not permanently jump ahead of unrelated waiting users
```

### Configuration

```text
invalid/zero/excessive ceiling rejected or clamped by explicit contract
runtime uses the stored effective ceiling
changing the ceiling affects future claims, not already running turns
```

## 8. Real gate mapping

The eventual P5.2 evidence should primarily close these existing Phase 5 hard gates:

```text
P5-REAL-MULTICHAT
P5-REAL-CONVERSATION-ORDERING
P5-REAL-BACKPRESSURE
```

It also supports `P5-REAL-UI-NONBLOCKING`, but P5.1 owns the frontend non-blocking state itself.

Measurements worth recording:

```text
configured capacity
effective capacity
peak simultaneous running turns
queue wait per turn
queued depth
user distribution under contention
claim/retry counts
no double-claim observations
```

## 9. Suggested implementation slices

Keep P5.2 small and reversible:

```text
P5.2a capacity + causal eligibility
  explicit ceiling
  race-safe claim decision
  same-conversation serialization
  focused concurrency tests

P5.2b release wake-up + fairness
  terminal/approval capacity release
  anti-starvation ordering
  focused load/fairness tests

P5.2c browser/real acceptance and operational visibility
  bounded scheduler diagnostics needed by gates
  real multi-chat/ordering/backpressure evidence
```

P5.1 is accepted. This preparation remains advisory: implementation must still establish the capacity,
ordering, fairness and recovery contracts with focused tests and real resource measurements.

## 10. Decisions deliberately deferred

Do not decide these without focused P5.2 measurements:

- exact maximum supported concurrency;
- whether the static cron slot pool should grow beyond two;
- advisory lock vs a tiny semaphore/control model;
- provider-specific concurrency metadata shape;
- whether fairness needs persisted scheduler state;
- whether polling/bus/SSE changes are useful for queue state.

Those decisions should be made from the P5.1-tested lineage plus focused P5.2 concurrency tests and
real resource measurements.
