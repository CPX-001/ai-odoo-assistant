# P5.8 — Semantic activity, reasoning-summary and navigation UX

Date: 2026-08-29  
Status: **TARGET / PRODUCT DESIGN — NOT IMPLEMENTED**  
Inspected baseline: `f92c959e19999b8b83d7111e84b85e5d70eba366` (`main`, P5.6 accepted; P5.7 ready/not started)  
Suggested ordering: after P5.7 and before Phase 6 unless implementation evidence shows that a smaller prerequisite belongs in P5.7.

This document records the product decisions for turning the current public-activity stream into a compact, natural, extensible work log. It also defines the seam that later web search, Evidence/RAG, source inspection, vision/files, TaskPlan and third-party Odoo addons should reuse.

It is intentionally a **target specification**, not an implementation claim and not a change to `EXECUTION_STATE.md`. The active roadmap cursor remains authoritative.

---

## 1. Product goal

The Assistant should not expose a chronological dump of technical capability lifecycle events. It should show a compact explanation of the work that a normal Odoo user can understand while still retaining a deeper developer/diagnostic view when requested.

Desired mental model:

```text
provider/runtime activity
        +
host capability lifecycle
        +
verified public result projections
        +
source/navigation references
        |
        v
semantic work items
        |
        +--> compact live headline
        +--> expandable user-facing reasoning/work log
        +--> optional technical/diagnostic detail
        +--> future TaskPlan progress surface
```

The product should feel closer to a modern agent UI than to an execution log.

### Representative target

While running, the collapsed headline continuously reflects the latest meaningful work:

```text
Razonando · Consultando contactos
Razonando · Preparando contactos de prueba
Razonando · Creando presupuestos
Razonando · Verificando resultados
```

The user can therefore understand progress without opening anything.

When expanded:

```text
Razonando
  Analizando la petición
  Prepararé 30 presupuestos de prueba y los contactos necesarios
  Consultando contactos existentes
  Creando contactos demo                     ✓
    Demo Acme
    Demo Northwind
    Demo Contoso
    Demo Alpine
    Demo Fabrikam
    Mostrar 5 más · Mostrar los 25 restantes
  Creando presupuestos                       ✓
    S00428 · Demo Acme · 29/08/2026
    S00429 · Demo Northwind · 29/08/2026
    ...
```

After completion the whole block collapses to something discreet such as:

```text
Ha pensado durante 32 s · 7 pasos
```

All deterministic wording must be translated using Odoo's language system. `Razonando` is the current Spanish product label, not a hard-coded protocol value.

## 2. Decisions captured from product review

The following decisions are intentional product requirements.

1. **The live headline changes.** Do not keep a static `Razonando` headline while work happens. The compact line should show the most recent meaningful semantic step so an observer can follow progress without expanding the log.
2. **Completed activity is collapsed and discreet.** Show total elapsed time and a compact step count, e.g. `Ha pensado durante 32 s · 7 pasos`.
3. **Use a hybrid of deterministic and model-generated wording.** Stable lifecycle labels should be host-owned; a concise provider/model summary may explain intent or a deeper investigation when it adds value.
4. **Default detail level is medium.** Show major steps plus relevant queries/actions, not every low-level event.
5. **Technical detail is hidden by default and configurable.** User, developer and operator profiles may select different defaults.
6. **Repeated operations are grouped when they represent one semantic operation.** Do not fill the chat with start/end pairs or dozens of equivalent queries.
7. **Odoo references should be navigable.** Records, models, views, actions and relevant configuration locations should be renderable as safe clickable references.
8. **Batch details are progressively disclosed.** Default to five rows, then `show 5 more`, plus an explicit `show remaining` action when safe. Rendering/transfer limits must block pathological expansions gracefully.
9. **Unknown-model row summaries are not purely hard-coded.** The host infers a candidate presentation from effective schema/metadata; the model may validate/refine the presentation contract using a bounded sample, then the same contract is reused for homogeneous records.
10. **Normal-user labels are the default.** Technical model/view names are configurable and belong to detailed/developer views unless context requires them.
11. **Web activity shows query + primary domain when known.** Multiple related searches are grouped; distinct concepts create distinct work items. Completed search groups expose consulted-source links.
12. **Evidence/RAG/source inspection uses an extensible activity taxonomy.** The UI should distinguish internal knowledge, current Odoo runtime, source tree/code, configuration, logs, web and other evidence families instead of reducing everything to `Buscando información`.
13. **Vision/file analysis may surface concise provisional observations.** The richer the task, the more useful a brief observation is, provided uncertainty is represented honestly.
14. **Phase 6 TaskPlan gets its own surface above the composer.** Example: `Paso 2/5`, expandable into `✓ Preparar contactos`, `⟳ Crear presupuestos`, `○ Verificar resultados`. Do not bury the TaskPlan inside the reasoning disclosure.
15. **Approvals remain visible outside the reasoning disclosure.** They can be linked to a work item/plan step but must never require expanding the reasoning area.
16. **Partial failures are first-class results.** E.g. `28 creados · 2 no completados`, with details and a later diagnostic capability/skill able to investigate why.
17. **Imperceptibly short verification should not clutter semantic history.** Keep it in telemetry/audit, but only show it as a work item above a configurable visibility threshold; initial target around 1–1.5 s.
18. **Total elapsed thinking/work time is always available after completion.** Per-step timings belong mainly to detailed/diagnostic views.
19. **Comfort/detail parameters should be configurable.** The protocol must support compact/normal/detailed/diagnostic presentations without duplicating runtime logic.
20. **Current product word is `Razonando`.** It may evolve later; store semantic codes, not Spanish literals as protocol identity.

## 3. Current-main diagnosis

The current P3/P5.4 foundation is valuable and should be extended rather than replaced:

- `PublicTurnEvent` is closed, bounded and rejects private `agent.thinking` activity.
- `odoo.ai.turn.live.event` is independently committed so progress is observable before the business transaction completes.
- capability execution emits lifecycle events around start/completion/failure.
- the browser has a persisted cursor and a separate answer-delta channel.

The current UX problem comes from projecting lifecycle events almost 1:1 into visible rows:

```text
tool.started   -> CapabilityDefinition.title
tool.completed -> CapabilityDefinition.title
```

Therefore a single call naturally appears twice and repeated calls can produce many nearly identical rows. The current event contract is also intentionally too small to express operation identity, parent/child relationships, rich safe result summaries or navigation/source references.

This is not a reason to remove P3 events. It is a reason to stop treating raw public lifecycle rows as the final product representation.

## 4. External reference findings

These references are design evidence only; CPX keeps Odoo as authority and does not import their runtimes.

### Odoo SaaS 19.4 — intermediate agent status

Odoo documents intermediate UI messages such as analyzing the request, consulting sources and preparing an action. This validates the product direction of displaying meaningful work classes instead of raw tool names.

Reference: `https://www.odoo.com/documentation/saas-19.4/fr/applications/productivity/ai/agents.html`

### OpenAI Codex App Server — readable reasoning summaries

The current App Server protocol distinguishes a `reasoning` item with `summary` and raw `content`, and exposes `item/reasoning/summaryTextDelta` plus summary-part boundaries. It explicitly describes those summary deltas as readable reasoning summaries. Raw reasoning has a different event (`item/reasoning/textDelta`).

The protocol/config schemas also expose reasoning-summary modes such as `auto`, `concise`, `detailed` and `none` where supported.

References:

- `https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md`
- `https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/json/v2/ConfigReadResponse.json`

**CPX rule:** only provider-supported readable summaries may enter the user-facing reasoning-summary seam. Never expose raw reasoning content or reconstruct chain-of-thought.

### Vercel AI SDK — UI state is not model state

`UIMessage` separates UI application state from model messages and uses typed parts for text, reasoning, tools, URL/document sources, files, data and step boundaries. `streamText` also carries stable `toolCallId`, tool results, reasoning and sources.

Useful pattern: keep a typed application/UI projection rather than making strings from provider events the protocol.

References:

- `https://ai-sdk.dev/docs/reference/ai-sdk-core/ui-message`
- `https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text`

### LangGraph/LangChain — multiple stream modes

The streaming API separates agent progress (`updates`), generated messages, custom application updates and task start/finish events. It also documents custom progress signals such as bounded record counts.

Useful pattern: provider text, semantic progress and task lifecycle do not have to be one stream type.

References:

- `https://docs.langchain.com/oss/python/langchain/streaming`
- `https://docs.langchain.com/oss/python/langgraph/streaming`

### OpenAI Agents SDK — traces/spans are hierarchical diagnostics

Tracing uses start/end timestamps and `parent_id` to organize workflows, turns, generations, function calls, guardrails and custom spans. It also separates sensitive content capture from structural metadata.

Useful pattern: semantic UI and diagnostic trace can share correlation IDs without exposing diagnostic content to normal users.

Reference: `https://openai.github.io/openai-agents-python/tracing/`

### Odoo 18 — translation runtime

Odoo 18 provides server-side translation (`env._` / `_`) and frontend `_t`, with fixed translatable format strings and runtime placeholder interpolation. Translation extraction requires stable literal templates rather than dynamically generated English strings.

References:

- `https://www.odoo.com/documentation/18.0/developer/reference/frontend/javascript_reference.html`
- `https://www.odoo.com/documentation/18.0/developer/howtos/translations.html`

This directly constrains the activity protocol: deterministic UI text must be represented by semantic keys/template arguments and translated under the effective Odoo language, not persisted as English-only truth.

### Project research snapshots

The Project Atlas v1.1 section 4.10 already recommends typed, sanitized public progress events and explicitly rejects streaming private reasoning. The Benchmark/Blueprint section 4.8 recommends semantic progress states and reusing the existing Odoo-native queue/events. This specification makes those earlier recommendations concrete and incorporates the later product preferences above.

## 5. Architecture direction

### 5.1 Preserve internal lifecycle; add a semantic projection

Do not delete the current lifecycle/audit path. Introduce a versioned user-facing projection above it:

```text
Internal events / provider events / receipts
                 |
                 v
        Public lifecycle facts
                 |
                 v
      SemanticActivityProjector
                 |
                 +--> PublicWorkItem updates
                 +--> PublicReasoningSummary updates
                 +--> PublicReference objects
                 |
                 v
               OWL
```

A normal user consumes `PublicWorkItem` state. Diagnostic mode may additionally inspect lower-level lifecycle/trace facts.

### 5.2 Stable operation identity

A capability call must have a host-generated stable `activity_id`/`operation_id` shared by start/update/completion/failure. Optional `parent_activity_id` and, later, `task_step_id` provide hierarchy.

Never deduplicate by string equality alone. Four separate `odoo.query_records` calls may be legitimately different operations.

Example conceptual contract:

```text
activity_id
parent_activity_id?
task_step_id?
category
status              # pending/running/completed/failed/partial/blocked
headline_code
headline_args
summary?
resource_refs[]
source_refs[]
result_summary?
started_at
ended_at?
diagnostic_ref?
```

`headline_code` is semantic protocol identity. `headline_args` contains bounded validated data. The localized sentence is produced at presentation time.

### 5.3 Work-item reducer instead of row-per-event

The browser/server projector should reduce lifecycle changes into one item:

```text
capability.started   operation=42 -> item 42 running
capability.completed operation=42 -> item 42 completed
```

The user sees one row whose state changes, not two rows.

Equivalent child operations may be grouped under a semantic parent, but grouping requires explicit correlation/semantic keys, not merely equal tool names.

### 5.4 Reasoning summary is a separate channel

Use three distinct concepts:

1. **Deterministic semantic activity** — host-owned and authoritative about what class of work is occurring.
2. **Readable reasoning/progress summary** — model/provider text intended for presentation; advisory, bounded and language-aware.
3. **Private/raw reasoning** — never public.

For Codex, consume `item/reasoning/summaryTextDelta` when the provider/model profile supports it. Explicitly ignore `item/reasoning/textDelta` for public UX.

If a provider does not support safe reasoning summaries, the UX remains useful from deterministic semantic activity alone.

### 5.5 Provider-neutral feature negotiation

Later `ProviderProfile` should describe:

```text
reasoning_summary: native | emulated | unavailable
reasoning_summary_detail: none | concise | detailed
source_events: native | emulated | unavailable
```

Do not make Codex-specific protocol names part of the frontend contract.

## 6. Headline and disclosure behavior

### Running

Collapsed view always shows the latest **meaningful visible** semantic item, with a subtle animation.

Examples after localization:

```text
Razonando · Analizando la petición
Razonando · Buscando "IVA intracomunitario 2026" en agenciatributaria.es
Razonando · Consultando contactos
Razonando · Analizando una imagen
Razonando · Creando presupuestos
```

Low-value sub-second internal work should not replace the headline unless no better activity exists.

### Completed

Default collapsed summary:

```text
Ha pensado durante <duration> · <visible_step_count> pasos
```

`visible_step_count` counts semantic user-facing items after grouping/filtering, not raw event rows.

### Visibility threshold

Add a configurable threshold for transient work, initial product target approximately `1200 ms` and bounded by administrator ceilings. Work below the threshold remains in diagnostics/telemetry but can be omitted from normal semantic history if it would only create flicker/noise.

Failure, approval, partial completion or security-relevant states bypass this cosmetic threshold.

## 7. Configurable detail and comfort settings

Design these as presentation settings, not authority settings. They may have user/profile defaults and administrator ceilings.

Suggested initial parameters:

```text
activity_detail_level = compact | normal | detailed | diagnostic
activity_batch_page_size = 5
activity_source_preview_count = 1
activity_transient_threshold_ms = 1200
activity_show_technical_names = false
activity_show_step_durations = false
activity_auto_expand_running = false
activity_auto_collapse_completed = true
activity_reasoning_summary = concise | detailed | off
```

Later useful bounds:

```text
max_rendered_activity_items
max_rendered_batch_rows
max_expand_all_rows
max_reference_count_per_item
max_reasoning_summary_chars
max_source_links_per_group
```

Normal Odoo users default to `normal` and human labels. Developer/Operator profiles may default to `detailed` and optionally reveal technical names. `diagnostic` is not simply "more reasoning"; it exposes structural lifecycle metadata, timings, capability/model identifiers and diagnostic codes while still excluding private reasoning/secrets.

Do not let a user preference disable safety/audit requirements.

## 8. Batch rendering and overload protection

A work item representing many records should use progressive disclosure.

Default example:

```text
30 presupuestos creados
  [first 5 rows]
  Mostrar 5 más
  Mostrar los 25 restantes
```

The final `show remaining` path is conditional. Before expanding, the host/UI estimates row count and bounded serialized/render cost. If the requested expansion crosses configured hard limits, block only the expansion and show a discreet explanation such as:

```text
No se muestran los 2.480 registros a la vez para evitar sobrecargar el navegador.
Puedes abrirlos en una vista de Odoo o cargarlos por bloques.
```

Prefer offering a navigable Odoo list/action reference for very large result sets instead of rendering thousands of chat rows.

This is presentation backpressure, not business-operation backpressure.

## 9. Generic Odoo record/model presentation

### 9.1 Goal

Unknown OCA/custom models must receive useful summaries without hard-coding every module.

### 9.2 Candidate inference

From effective schema and runtime metadata, infer a bounded candidate presentation:

```text
human model label
_rec_name / display_name
likely identifier/reference field
1–3 descriptive fields
state/status when useful
business date when useful
relations suitable for display
```

All candidate fields must already be readable under the effective user.

### 9.3 Model-assisted validation

Do not make the presenter completely deterministic. For a new `(model, schema_fingerprint, language, presentation_profile)`:

1. host infers a candidate display spec;
2. host reads one bounded representative record/sample through normal authority;
3. model validates/refines which safe fields form a useful concise row;
4. host validates the returned presentation spec against the effective schema;
5. reuse/cache that spec for homogeneous records while the fingerprint remains valid.

The model chooses **presentation**, not field access or authority.

A trusted addon may later provide an explicit presenter/metadata hook that takes precedence over model inference.

## 10. First-class clickable references and Odoo navigation

References should be reusable outside the reasoning log and become a general response capability.

Conceptual `PublicReference` kinds:

```text
odoo_record
odoo_model
odoo_view
odoo_action
odoo_menu
odoo_setting
source_file
source_symbol
web_url
document
attachment
```

The model may request/propose a reference, but the host resolves it to a safe typed target. Never trust arbitrary model-generated Odoo routes.

For Odoo references, validate existence and access before rendering. Prefer a structured navigation descriptor that the OWL client turns into an Odoo action/navigation operation.

Target examples:

```text
S00428                          # opens sale.order record
Presupuestos                    # opens permitted list/action
Configuración > Ventas > ...    # opens the resolved configuration action/view
sale.view_order_form            # optional technical label in developer mode
```

A future installation-intelligence query such as:

> ¿En qué vista se encuentra la opción X?

should be able to return:

```text
He encontrado la opción X en "Ajustes de Ventas" [open]
Vista técnica: sale.res_config_settings_view_form [developer detail]
```

This requires future Phase-8 view/menu/action/source intelligence for grounding, but the reference/navigation contract should be designed now so all surfaces can reuse it.

## 11. Web search presentation

Represent search work by **concept/search group**, not one noisy row per HTTP/provider search.

Primary collapsed item:

```text
Buscando "IVA intracomunitario 2026" en agenciatributaria.es y 6 más
```

Expanded children can show one line per actual search/query/source group. Create a new top-level semantic row when the search moves to a materially different concept, not merely another domain for the same question.

On completion, expose bounded source links as `PublicReference(web_url)` entries. Source references and final-answer citations may share identity/provenance but are different presentation surfaces.

Do not expose raw search-provider payloads.

## 13. Vision and file observations

For complex image/file tasks, the reasoning-summary seam may include a short provisional observation when it explains the next action:

```text
Analizando imagen
La imagen parece corresponder a una factura de proveedor; comprobaré los datos en Odoo.
```

Such observations are advisory and must preserve uncertainty (`parece`, `sugiere`, etc.) until grounded. Deterministic statements about Odoo records still require host/runtime evidence.

## 14. Phase 6 TaskPlan surface

Semantic activity is not the same as TaskPlan.

When Phase 6 introduces a mutable high-level `TaskPlan`, show a compact independent control above the composer/input area:

```text
Paso 2/5  ▾
```

Expanded:

```text
✓ Preparar contactos
⟳ Crear presupuestos
○ Verificar resultados
○ Revisar incidencias
○ Resumir el resultado
```

TaskPlan can evolve/replan as new evidence appears. Each semantic work item may reference `task_step_id` so the user can understand which current activity belongs to which plan step.

TaskPlan has no execution authority. `EffectPlan` continues through host validation/approval/verification.

## 15. Approval, failure and self-diagnosis

### Approval

Approval cards remain top-level actionable UI, outside the reasoning disclosure. Link them to the relevant `activity_id`/`task_step_id` for context.

### Partial batch failure

Represent partial outcomes explicitly:

```text
30 intentados · 28 creados · 2 no completados
```

Show the failed subset through bounded details/reference rows.

### Failure diagnosis

Later Skills/capabilities should allow the Assistant to inspect its own **public execution facts, receipts, diagnostic codes, safe trace references and relevant Odoo evidence** and explain likely failure causes.

Do not give the model raw secrets, provider stdout or unrestricted logs merely to support self-diagnosis. Diagnosis remains evidence-driven and host-bounded.

## 16. Internationalization is a hard design requirement

Every deterministic user-visible phrase must follow Odoo language semantics.

### Rules

1. Protocol/state identity uses stable codes, never Spanish/English phrases.
2. Deterministic templates use Odoo translatable literals and runtime placeholders (`env._` / frontend `_t`).
3. Dynamic Odoo model/field/action labels are resolved under the effective/captured Odoo language.
4. Provider/model-generated summaries are requested in the turn's captured Odoo language.
5. Persist semantic facts and safe arguments; translate as late as practical so history can render consistently after language changes.
6. Do not build phrases by concatenating individually translated fragments. Use complete format strings with placeholders.
7. Plural/count-sensitive templates must use proper Odoo translation patterns.
8. Technical identifiers remain untranslated when shown in developer/diagnostic mode.

P5.6 already carries a bounded captured Odoo-language fallback in conversation context. P5.8 should reuse that direction rather than inventing a parallel language setting.

### Example

Persist conceptually:

```text
headline_code = "activity.query.records"
args = {"model_label": "Contactos", "count": 14}
```

Do **not** persist protocol identity as:

```text
"Query Odoo records"
"Consultando contactos"
```

Those are renderings.

## 17. Suggested implementation slices

Do not implement this as one frontend-only rewrite. Suggested coherent slices after the active P5.7 work is accepted:

### P5.8a — operation correlation + semantic reducer

- versioned `activity_id` correlation across started/completed/failed;
- reducer/upsert semantics;
- remove visible start/completion duplication;
- live headline follows latest meaningful item;
- completed collapsed duration + semantic step count.

### P5.8b — localization + configurable presentation profile

- semantic label codes/args;
- Odoo-language translation seam;
- normal/detailed/diagnostic modes;
- transient visibility threshold;
- batch page-size/renderer bounds.

### P5.8c — reasoning summaries

- Codex readable summary integration;
- strict rejection of raw reasoning content;
- provider feature negotiation/fallback;
- bounded summary length and language behavior.

### P5.8d — references + generic presenters

- safe `PublicReference` contract;
- record/model/action/view navigation resolution;
- generic schema-driven presentation spec;
- bounded model validation/cache keyed by schema fingerprint;
- batch `show more` and list-view fallback.

Phase 6 then consumes the correlation/reference foundation for TaskPlan hierarchy and multi-step effects.

If investigation shows one of these slices must precede P5.7 for architectural reasons, update the roadmap explicitly; do not silently mix it into P5.7.

## 18. Failure modes and hard bounds

The design must explicitly cover:

- duplicate/out-of-order lifecycle updates;
- reconnect/replay without duplicating work items;
- activity item started but no terminal update because the turn failed;
- unsupported provider reasoning summaries;
- malformed/oversized summary text;
- model-generated presentation spec referencing unavailable fields;
- stale schema fingerprint;
- record removed or ACL revoked after a reference was created;
- huge batches that exceed render/transport limits;
- web/source links that become stale;
- language changed between original turn and later history rendering;
- child activity whose parent is unavailable after bounded retention;
- partial success where some records were committed and others failed;
- approval/recovery states that must remain visible regardless of cosmetic filtering.

No semantic projection failure may change capability authorization or business-effect success.

## 19. Acceptance tests/evals to require

At minimum:

### Deterministic

- one started+completed capability call renders one semantic work item;
- independent identical tool calls do not merge accidentally;
- grouped children maintain stable ordering after reconnect;
- latest meaningful work item updates the collapsed headline;
- completed summary reports total duration and semantic step count;
- sub-threshold verification is absent from normal history but present in diagnostic facts;
- approval/failure/partial states ignore transient hiding;
- batch page size defaults to 5 and `show more` preserves cursor/order;
- over-limit `show remaining` is blocked gracefully and offers a list/navigation alternative;
- record references fail closed when ACL is revoked;
- normal mode hides technical names; developer mode can show them;
- Spanish/English users receive translated deterministic labels from the same semantic event;
- technical identifiers remain stable/untranslated;
- raw Codex `item/reasoning/textDelta` can never appear in public/browser activity;
- bounded `summaryTextDelta` can appear only through the reasoning-summary channel;
- unknown OCA/custom model presenter uses only effective-schema fields and survives fingerprint change by revalidation.

### Product/evals

Cover at least:

- deep read-only investigation;
- 30-record demo creation once Phase 6 can represent the required multi-step effect;
- 300-record batch with progressive disclosure;
- partial batch failure + diagnostic follow-up;
- web research across one concept and across multiple concepts;
- internal knowledge + current-runtime + source-code mixed evidence;
- image/file observation followed by Odoo grounding;
- "where is setting X?" returning a clickable action/view reference;
- normal-user vs developer-detail presentation;
- Spanish and English full-turn UX;
- reconnect while a nested semantic operation is running.

### Proposed real gates

Names are provisional until incorporated into the active playbook:

```text

P5-REAL-REASONING-SUMMARY
P5-REAL-ACTIVITY-I18N
```

## 20. Non-goals

P5.8 does **not** by itself:

- implement Phase-6 multi-step EffectPlan;
- grant access to arbitrary Odoo methods/routes;
- expose private chain-of-thought;
- add general web search/RAG/vision if their capabilities do not yet exist;
- implement Phase-8 source/view/menu intelligence;
- change business authority, ACL, approval or write-barrier semantics;
- require SSE/WebSocket transport;
- make diagnostic mode a raw provider-console viewer.

It defines the presentation/correlation/reference seams those later features will reuse.

## 21. Decision summary

The product should evolve from:

```text
technical chronological event log
```

into:

```text
live semantic headline
+ compact expandable work log
+ safe readable reasoning summaries
+ typed clickable Odoo/source references
+ progressive batch detail
+ configurable user/developer detail
+ fully Odoo-localized deterministic text
+ diagnostic trace kept structurally separate
```

The existing P3 live persistence and host-owned authority remain the foundation. The required reform is primarily a **versioned semantic projection/correlation layer**, not a new runtime or transport.
