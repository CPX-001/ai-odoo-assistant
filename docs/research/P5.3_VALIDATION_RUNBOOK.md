## 4. Combined final acceptance battery

The repository provides one orchestrator for everything still required before P5.4:

```bash
python tests/e2e/p5_3_acceptance_batch.py
```

Machine-readable real-gate contract:

```text
tests/e2e/p5_3_real_gates.json
```

The batch requires:

```text
ODOO_BIN
ODOO_CONF
ODOO_AI_ADDONS_PATH
ODOO_AI_P5_BASE_URL
ODOO_AI_P5_DB
ODOO_AI_P5_LOGIN
ODOO_AI_P5_PASSWORD
```

`ODOO_AI_P5_DB` must use the disposable `odoo_ai_*` prefix. `ODOO_AI_P5_BASE_URL` must be a loopback HTTP origin such as `http://127.0.0.1:8069`; the runner deliberately refuses to launch a managed validation server on a remote interface.

For local Odoo installations that need extra CLI switches, the runner accepts optional shell-split arguments through:

```text
ODOO_AI_P53_ODOO_TEST_ARGS
ODOO_AI_P53_ODOO_SERVER_ARGS
```

The required database/addons/test/server safety arguments remain host-owned by the runner and are appended after those optional adjustments.

### 4.1 Preflight and exact-SHA ownership

The batch first requires a clean worktree and executes:

```text
node --check tests/e2e/p5_3_settings_snapshot_browser.mjs
python -m json.tool tests/e2e/p5_3_real_gates.json
git diff --check
git rev-parse HEAD
```

A dirty worktree is rejected because the tested SHA must identify the exact content under validation.

### 4.2 `P5.3-FULL-ADDON-REGRESSION`

The batch runs the complete addon regression first, while no long-lived Odoo HTTP process is needed:

```bash
"$ODOO_BIN" -c "$ODOO_CONF" -d "$ODOO_AI_P5_DB" \
  --addons-path="$ODOO_AI_ADDONS_PATH" \
  -u odoo_ai_assistant \
  --test-enable --test-tags '/odoo_ai_assistant' \
  --stop-after-init --log-level=test
```

The runner requires process success and parses Odoo's final test totals. Acceptance requires a positive test count, `0 failed`, and `0 error(s)`.

Running the full addon regression first is intentional: it avoids spending provider/browser time on a lineage that is already deterministically broken, and leaves the same updated database ready for the real product-path gate.

### 4.3 Managed real Odoo server

After the full addon battery passes, the runner starts one isolated loopback Odoo process against the same disposable database with:

```text
workers = 0
max cron threads = 2
configured addon path
configured Odoo data_dir / Codex authentication
```

It refuses to start if the requested loopback URL is already serving Odoo, waits up to 60 seconds for `/web/login`, and terminates the managed process after the browser gate. The complete server log stays in a temporary local file; it is not committed as evidence automatically.

### 4.4 `P5-REAL-SETTINGS-SNAPSHOT`

The batch then runs:

```bash
node tests/e2e/p5_3_settings_snapshot_browser.mjs --gate P5-REAL-SETTINGS-SNAPSHOT
```

The browser gate must prove through the real Odoo Assistant UI/product path:

```text
start unresolved Turn A with model/profile A
read A.reasoning_model, A.policy_payload and A.execution_settings_payload
prove execution_settings_payload.format_version == 1
prove snapshot model/profile/policy agree with A's persisted fields
change model/profile through the real Assistant UI while A remains unresolved
prove A's complete execution_settings_payload is unchanged
submit Turn B in a new conversation
prove B captures model/profile B in execution_settings_payload v1
prove B.execution_settings_payload.policy equals B.policy_payload
```

The fixture is deliberately read-only. Same-turn approval/requeue retention after a preference change remains covered by the accepted deterministic regression rather than creating a business mutation only for this browser gate.

A successful browser runner prints `OBSERVED_OK_NOT_AUTOMATIC_PASS`. The combined batch therefore finishes as:

```text
PASS_PENDING_EVIDENCE_REVIEW
```

It does **not** silently convert the browser observation into formal roadmap acceptance.

## 5. Failure handling

If either remaining gate fails:

1. diagnose the actual root cause;
2. repair the smallest responsible production or harness layer without weakening the contract;
3. rerun the failed gate;
4. if production/model/test behavior changed, rerun the relevant focused/deterministic P5.3 coverage;
5. rerun the combined acceptance batch on the repaired clean SHA before acceptance;
6. record the repair and final evidence on one coherent lineage.

Do not advance P5.4 with an unresolved browser or full-addon failure.

## 6. Evidence and exit
