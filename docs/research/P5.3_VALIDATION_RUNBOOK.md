## 3. Bounded deterministic regression — PASS

Validation ID:

```text
P5.3-DETERMINISTIC-REGRESSION
```

The regression selector is intentionally method-level so this gate stays small. Execute these exact contracts when the local Odoo test selector supports method-level targeting; otherwise run only their containing classes:

```text
TestAssistantTurnQueue.test_enqueue_persists_user_turn_and_initial_event
TestAssistantTurnQueue.test_enqueue_is_idempotent_for_client_request_id
TestAssistantUserPreferences.test_reasoning_model_is_owned_by_current_user
TestAssistantChatPolicy.test_effective_capability_policy_uses_user_autonomy_once
TestCapabilityActions.test_approve_requeues_same_turn_with_bound_authorization
TestAssistantTurnSettingsSnapshot.test_runtime_codex_settings_use_captured_turn_model
```

These cover, respectively:

```text
normal enqueue persistence
client-request idempotency
user-owned model preference isolation
profile -> resolved policy mapping
approval -> same persisted turn with original captured model/policy after preferences change
embedded runtime Codex settings reading the persisted turn model rather than current user preference
```

The approval regression observes that changing the user from model/profile A to B while the plan waits for confirmation does not replace the turn, mutate its snapshot, or make the approval response use profile B. The runtime-consumption regression patches only Codex discovery/path facts; it does not start a provider process and proves `_codex_settings(turn)` receives model A from the persisted turn.

## 4. Current next validation slice — formal real product-path gate

Validation ID:

```text
P5-REAL-SETTINGS-SNAPSHOT
```

The dedicated runner is:

```text
tests/e2e/p5_3_settings_snapshot_browser.mjs
```

and its machine-readable contract is:

```text
tests/e2e/p5_3_real_gates.json
```

The runner deliberately reuses the already proven P5.1 browser interaction shape, but now reads and validates the P5.3 versioned `execution_settings_payload` itself. It must prove through the real Odoo browser/product path:

```text
start unresolved Turn A with model/profile A
read A.reasoning_model, A.policy_payload and A.execution_settings_payload
prove execution_settings_payload.format_version == 1
prove execution_settings_payload.model/profile/policy agree with A's persisted fields
change model/profile through the real Assistant UI while A remains unresolved
prove A's complete execution_settings_payload is unchanged
submit Turn B in a new conversation
prove B captures model/profile B in execution_settings_payload v1
prove B.execution_settings_payload.policy equals B.policy_payload
```

The browser fixture is intentionally read-only, so approval is not applicable inside this real gate. Same-turn approval/requeue retention after a preference change is already covered by the preceding deterministic regression and must remain part of the accepted P5.3 evidence chain.

Preflight the harness before the real run:

```bash
node --check tests/e2e/p5_3_settings_snapshot_browser.mjs
python -m json.tool tests/e2e/p5_3_real_gates.json >/dev/null
git diff --check
```

Use the same disposable P5 environment variables as the accepted P5.1 product-path validation:

```text
ODOO_AI_P5_BASE_URL
ODOO_AI_P5_DB
ODOO_AI_P5_LOGIN
ODOO_AI_P5_PASSWORD
```

The database must use the `odoo_ai_*` disposable prefix. Update the addon on the exact SHA under test, start Odoo with the supported authenticated Codex runtime, then execute only this gate:


A successful runner prints `OBSERVED_OK_NOT_AUTOMATIC_PASS`; formal PASS requires reviewing and recording sanitized evidence. The prior `P5.1-BROWSER-SETTINGS-SNAPSHOT` PASS remains supporting context only and is not automatic PASS for this SHA/contract.

If this gate fails, repair the smallest responsible P5.3 or harness layer, rerun the gate, and do not compensate by starting P5.4.
