# P5.4 final UX validation runbook

Date: 2026-08-29  
Status: implementation present; local validation is next

This runbook intentionally batches P5.4 validation into useful chunks instead of micro-checkpoints.

## 1. Exact lineage

Pull current `main`, record the exact SHA and update `odoo_ai_assistant` on a disposable Odoo 18 Community database. The P5.4 implementation is frontend-only and bumps the addon version to `18.0.10.13.0`.

## 2. Local/deterministic acceptance battery

Run the following as one batch where the environment supports it:

```bash
cd "$REPO"
node --check tests/e2e/p5_4_final_ux_browser.mjs
python -m json.tool tests/e2e/p5_4_real_gates.json >/dev/null
python -m compileall -q addons/odoo_ai_assistant tests
python -m pytest -q tests/unit
node tests/js/failure_contract_test.mjs
node tests/js/public_activity_contract_test.mjs
git diff --check
```

Then update/install the addon and run the complete Odoo test battery:

```bash
"$ODOO_BIN" -c "$ODOO_CONF" -d "$ODOO_AI_P5_DB" \
  --addons-path="$ODOO_AI_ADDONS_PATH" \
  -u odoo_ai_assistant \
  --test-enable --test-tags '/odoo_ai_assistant' \
  --stop-after-init --log-level=test
```

Run the full `@odoo_ai_assistant` HOOT suite. The new focused contract is:

```text
assistant_final_ux_contract.test.js
```

Required local observations:

```text
final answer reconciliation is idempotent
one turn cannot retain duplicate local final-answer messages
activity and answer streaming remain independent channels
real activity suppresses the generic waiting fallback
approval/failure/recovery remain explicit states
P2-P5.3 frontend regressions remain green
```

Validation IDs:

```text
P5.4-DETERMINISTIC-FINAL-UX
P5.4-FULL-ADDON-REGRESSION
P5.4-HOOT-REGRESSION
```

If any local gate fails, repair the smallest responsible P5.4/frontend layer and rerun the affected battery before real-browser acceptance.

## 3. Real browser basic-chat gate

Use the same disposable P5 environment variables as P5.1/P5.3:

```text
ODOO_AI_P5_BASE_URL
ODOO_AI_P5_DB
ODOO_AI_P5_LOGIN
ODOO_AI_P5_PASSWORD
```

The database must use the `odoo_ai_*` prefix. Start the supported real Odoo + authenticated Codex path, then run:

```bash
node tests/e2e/p5_4_final_ux_browser.mjs --gate P5-REAL-CHAT-BASIC
```

Required observations:

```text
user message visible before enqueue response completes
real public activity becomes visible
activity is outside Assistant prose bubbles
no Pensando… bubble while real activity exists
turn completes successfully
exactly one final Assistant message remains
activity settles separately from the final answer
```

The runner prints `OBSERVED_OK_NOT_AUTOMATIC_PASS`; review its bounded output before recording formal PASS.

## 4. Error and recovery UX regression

P5.4 does not create a second failure injector. Reuse the already accepted current embedded-product Phase 2 fixtures on the P5.4 SHA:

```bash
node tests/e2e/phase2_real_failure_browser.mjs --gate P2-REAL-TIMEOUT
node tests/e2e/phase2_real_failure_browser.mjs --gate P2-REAL-TOOLFAIL
node tests/e2e/phase2_real_failure_browser.mjs --gate P2-REAL-RECOVERY
```

Review them as current-lineage evidence for:

```text
P5-REAL-ERROR-UX
P5-REAL-RECOVERY-UX
```

The failure UI must remain an explicit failure surface and recovery must remain explicit, uncertain and non-replayable.

## 5. Approval UX gate

`P5-REAL-APPROVAL-UX` is also HARD. Exercise an actual current embedded-product turn that reaches `awaiting_confirmation` under a disposable user/record and verify through Chromium that:

```text
approval is shown as a dedicated state, not Assistant prose
preview/step/risk information remains visible
Continue and Cancel are bound to the same persisted turn
changing other UI preferences does not replace that turn
no business write occurs before approval
```

Use existing bounded action fixtures/capabilities where possible; do not revive sidecar-era M6 authority or create a generic method-execution shortcut merely for validation. If the current environment cannot produce this path reproducibly, record `BLOCKED` and improve only the validation fixture/harness before claiming P5.4 acceptance.

## 6. Evidence / exit

For each gate record:

```text
validation id
exact tested SHA
Odoo/PostgreSQL/Python versions
Codex/Node/Playwright/Chromium versions where applicable
actual test/assertion totals
PASS | FAIL | BLOCKED
sanitized observations
repairs made
```

Do not store credentials, raw prompts/answers, provider internals, policy payloads or customer data.

P5.4 becomes `COMPLETE` only when the local battery and these HARD real gates are accepted on one coherent lineage:

```text
P5-REAL-CHAT-BASIC
P5-REAL-ERROR-UX
P5-REAL-APPROVAL-UX
P5-REAL-RECOVERY-UX
```

Only then may P5.5 post-effect reasoning consume the completed final-UX contract.
