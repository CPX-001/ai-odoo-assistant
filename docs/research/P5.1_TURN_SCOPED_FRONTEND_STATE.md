# P5.1 — Turn-scoped frontend/background state

Date: 2026-08-28  
Phase: 5 — natural non-blocking multi-chat product  
Slice: `P5.1-turn-scoped-frontend-state`  
Inspected starting `main`: `3908ac7886e8c2c2a5435d61d32c8ee523b6f019`  
State: `COMPLETE`

## Objective

Replace panel-global execution ownership with a turn/conversation-scoped frontend state while preserving the accepted P2 structured-failure, P3 public-activity and P4 provisional-answer contracts.

This slice is deliberately frontend-scoped. It does **not** implement P5.2 scheduler capacity/backpressure, P5.3 settings persistence semantics beyond the already-captured backend turn snapshot, post-effect reasoning or the future ConversationContextManager.

## Starting problem confirmed in code

Before this slice the browser used one mutable set of fields for every chat:

```text
state.loading
state.decisionLoading
state.result
state.actionReceipt
state.failure / errorCode
state.streamingText
state.activityEvents / currentActivity
state.messages
```

That global ownership disabled conversation navigation, the composer, model selection and autonomy selection while the visible turn was running. The backend already had durable independent turns and two queue workers, so the browser was the immediate product bottleneck.

## Implemented contract

The frontend now keeps an in-memory scope per conversation (plus a temporary scope for a not-yet-bound new chat):

```text
ConversationTurnScope
  key
  conversationId
  turnId
  turnState
  loading / decisionLoading
  result / actionReceipt
  failure / errorCode
  streamingText
  activityEvents / currentActivity
  lastSubmittedMessage
  messages
```

Existing panel fields remain only the **projection of the currently visible scope**. This is a compatibility bridge so the accepted P2-P4 templates/contracts do not need a parallel rendering system.

### Binding a new chat

A new chat starts with a temporary `new:N` scope. As soon as the durable `/odoo_ai/v1/turn` call has persisted the turn, the existing streaming client emits the `turn_persisted` timing point. The scope resolves `/odoo_ai/v1/turn/status`, obtains the server-owned `conversation_id`, and is rebound to `conversation:<uuid>`.

The extra status read is best-effort. A transient failure does not fail the durable turn; the final validated `normalizeChatResponse` result also carries the conversation binding and completes the rebind.

### Background isolation

Activity, answer deltas, final responses and failures mutate the owning scope. They are copied to the legacy visible panel fields only when that scope is still active. Switching to Chat B therefore cannot cause a late delta/failure from Chat A to overwrite Chat B.

### Approval/recovery isolation

Approval and recovery status calls use the existing host-safe `submitActionDecision` / `submitActionRetry` helpers, but with the owning conversation scope as their state object. No new effect authority is introduced and browser state still cannot execute a capability directly.

### Navigation and settings

While Chat A runs, the UI can now:

- open history;
- start a new chat;
- open another conversation;
- close/reopen the panel without cancelling the background promise;
- change the selected reasoning model;
- change the autonomy profile.

The current chat composer remains disabled only when **that chat's** scope is busy/recovery-bound. Model/autonomy changes still affect future turns only because the backend already snapshots `reasoning_model` and policy data when a turn is enqueued.

Conversation history can display compact in-page runtime labels:

```text
En cola
En curso
Esperando aprobación
Falló
Revisar recuperación
Completado
```

These labels are a frontend projection, not execution authority.

## Invariants preserved

- Odoo remains operational/persistence authority.
- P2 `FailureEnvelope` remains the browser failure contract.
- P3 public activity remains the bounded host projection; no private reasoning/raw provider data is added.
- P4 answer deltas remain provisional; final `normalizeChatResponse` validation remains authoritative.
- Capability/approval/write/verification authority is unchanged.
- A running turn keeps the model/policy snapshot captured by the backend enqueue path.
- No parallel backend queue, capability registry or transport was introduced.
- Same-conversation frontend submissions remain serialized by that conversation scope.

## Failure modes considered

- late Chat A delta after switching to Chat B -> retained only in A scope;
- new-chat turn receives durable conversation UUID after enqueue -> temporary scope is rebound;
- transient binding-status read fails -> final validated response can still bind the scope;
- user changes model/autonomy while A runs -> affects future enqueue only;
- approval/recovery state in A -> stored with A and restored when A is selected;
- close/reopen while a turn runs -> scope remains in the web-client service and server work is not cancelled/restarted.

## Deterministic tests added

`assistant_turn_scope_service.test.js` covers:

1. Chat B projects idle state while Chat A remains running.
2. Returning to A restores its partial answer and public activity.
3. Temporary new-chat state rebinds to durable conversation/turn IDs.
4. Compact conversation runtime-state/label mapping.
5. Reopening a scoped chat preserves the model-catalog refresh hook.
