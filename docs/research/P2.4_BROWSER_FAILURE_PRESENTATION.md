## Objective

Consume validated `browser_status().failure` without trusting arbitrary browser input, preserve its
machine semantics through polling/streaming, and render deterministic recovery guidance without
weakening the write barrier.

## Implemented browser contract

`static/src/services/assistant_failure_contract.js` mirrors the exact 11-field `FailureEnvelope`,
closed taxonomies and host limits. Invalid, mismatched, sensitive-key or oversized details fail
closed; only a bounded compatibility code may survive.

`assistant_stream_client.js` carries terminal structured failures. The streaming panel no longer
converts every unknown bounded thrown code to `service_unavailable`; provisional text is still
discarded on failure.

Presentation is deterministic and never renders provider text, `safe_summary` or `safe_details`.
Only stable code and diagnostic id may be technical detail. Authentication, Odoo ACL, provider
connection/capacity, capability, verification and recovery receive distinct behavior.

Retry is available only when:

```text
retryability == safe
effect_state in {none, not_started}
user_action == retry
```

`partial`/`unknown` and `recovery_required` never expose blind retry.

## Recovery-state browser hardening

Review after the first P2.4 publication found one fail-closed gap: a structurally valid but
inconsistent `recovery_required` browser status could theoretically carry `retryability=safe`,
`effect_state=none`, `user_action=retry`. The backend normally cannot produce that combination, but
the browser must never loosen the write-barrier authority even if a response is stale, corrupt or
manipulated.

`13b27c8bfe9c45b8f0ac92734d066a18eacc022f` therefore makes terminal state authoritative at the
browser boundary:

```text
state == recovery_required
  -> effect_state = partial if already partial, otherwise unknown
  -> retryability = never
  -> user_action = review
  -> browser retry control = unavailable
```

The browser can tighten recovery semantics but cannot declare an uncertain write effect safe.
HOOT and dependency-light regressions cover the rule.

## Real-gate fault fixture

The real Phase 2 gates no longer have to depend on random provider/network failures. A dedicated
test-only Odoo addon now lives at:

```text
tests/fixtures/odoo18/odoo_ai_phase2_faults
```

It is outside the product addon and is inert unless both:

```text
ODOO_AI_PHASE2_FAULT_FIXTURE=1
database name starts with odoo_ai_
```

are true. Exact test messages inject the five terminal families after the normal `/turn` account
gate and on the real persisted turn/cron path. The ACL scenario performs a real ORM read under the
originating `su=False` user. The recovery scenario persists only the turn write barrier; it commits
no business record effect.

`tests/e2e/phase2_real_failure_browser.mjs` then exercises the real Chromium UI and verifies the
actual terminal `/turn/status` envelope, deterministic browser copy, retry-control visibility and
redaction. It deliberately reports `OBSERVED_OK_NOT_AUTOMATIC_PASS`; evidence review against the
exact tested SHA is still required before a roadmap gate becomes PASS.

Exact setup and cleanup commands are in `PHASE23_REAL_VALIDATION_RUNBOOK.md`.
