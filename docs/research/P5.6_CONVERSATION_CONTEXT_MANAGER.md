# P5.6 ConversationContextManager

Date: 2026-08-29  
Status: complete and accepted through `720102f2a13af5240c779b07cc71ee65994a87b1`

## Why this is one slice

P5.6 is intentionally implemented as one coherent product slice rather than splitting recent messages, summary state, references and continuity into separate micro-phases. They are one contract: the reasoning provider needs a bounded Odoo-owned view of the conversation that remains causally correct across queued turns, reconnects, retries and post-effect continuation.

The next stop is therefore a real validation boundary, not another implementation sub-slice.

## Problem in the previous implementation

The old provider context was a fixed recent-message concatenation. It searched persisted messages by creation order while excluding only the current user message.

That is insufficient once Phase 5 allows a later message to be queued while the previous turn is still running:

```text
Turn A user message
Turn B user message is queued
Turn A Assistant answer is persisted later
```

Raw message id/time order is then not the same as conversation causality. A context builder based only on message chronology can place B before A's answer, or expose future same-conversation input to the wrong turn.

It also had no first-class place for:

```text
rolling structured summary
active record/model references
verified-effect references
future evidence references
conversation/session settings
```

## Implemented contract

`odoo.ai.turn.conversation_context_payload` is a versioned, bounded, host-managed checkpoint captured the first time a turn needs provider context.

Snapshot v1 contains:

```text
format_version
conversation_id
revision
recent_messages
rolling_summary
active_refs
evidence_refs
verified_effect_refs
session_settings
```

The provider port still accepts the historical keyword `conversation_summary` for compatibility with the frozen `ReasoningProvider` conformance contract, but its current product value is now compact structured JSON rather than one flat transcript string.

No Codex thread is used as conversation persistence authority.

## Causal construction

Context is built from predecessor **turn identity/order**, not raw message timestamps.

For the current turn:

1. search only same-conversation turns with lower durable turn id;
2. reject a non-terminal causal predecessor rather than reason across an impossible future;
3. reuse the newest predecessor context checkpoint when one exists;
4. fold that predecessor outcome and later terminal predecessors into the rolling state;
5. rebuild recent raw messages in causal `turn -> user message -> Assistant message` order;
6. exclude the current turn and every later turn;
7. add the current bounded screen record/model references;
8. freeze the resulting snapshot on the turn.

This matches P5.2's one-active-causal-turn-per-conversation rule.

## Rolling state

The rolling summary is deterministic and host-derived. It stores bounded terminal turn facts:

```text
turn id
terminal state
bounded user-intent excerpt
bounded Assistant-outcome excerpt
sanitized failure code when present
```

It is not an LLM-authored replacement for message history. Full `odoo.ai.message` rows remain authority.

The checkpoint also carries bounded active model/record refs and completed capability-step refs. Effect refs contain identity/state only; they do not copy raw write results or provider output.

`evidence_refs` is present as the P5.6 continuity slot but currently has no producer because the general EvidenceProvider/RAG work is later.

`session_settings` is likewise a bounded host-owned slot. P5.6 records the captured Odoo user-language fallback; P5.7 owns explicit conversation-scoped preference transitions and the full response-language policy.

## Turn stability

Once `conversation_context_payload` exists, ordinary writes cannot replace it. Approval resume and P5.5 post-effect continuation therefore reuse the same pre-turn conversation context.

Current-turn verified effect details continue to enter the same-turn working transcript through P5.5's authoritative `verified_effect_receipt`; they are not back-filled into the pre-turn context snapshot.

The next turn folds the completed predecessor effect reference into its conversation checkpoint.

## Bounds

Current v1 bounds are deliberately small:

```text
predecessor checkpoint scan: 24 turns
recent raw messages:         6
rolling summary entries:     6
active refs:                 8
verified effect refs:        8
evidence refs:               8
provider context string:     <= 8,000 chars
```

When the encoded context exceeds the provider seam budget, old recent/summary/reference items are dropped in a deterministic order. This is context compaction, not deletion of authoritative Odoo history.

## Security and authority

The context payload is data, not authorization.

It does not change:

```text
effective user / su=False
ACLs or record rules
capability availability
policy/approval
write barriers
verification
provider credentials
```

The field is host-managed and immutable after capture. It contains bounded conversation-derived data only and is supplied to the provider under the existing untrusted-data contract.

No generic ORM, SQL, Python or shell capability is introduced.

## Reference patterns used

The Project Atlas recommends bounded just-in-time context and separation of Conversation, Turn and InvocationContext instead of dumping whole records/history. Its Odoo/MuK comparison also points to semantic per-turn context refresh while keeping authority in Odoo.

The Blueprint's target stack places `INVOCATION + CONTEXT` before the effective capability catalog and keeps one common runtime for chat and later surfaces. P5.6 implements that continuity layer without introducing a second agent framework, vector store or sidecar.

## Real continuity gate prepared

`tests/e2e/p5_6_continuity_browser.mjs` implements `P5-REAL-CONTINUITY`.

The browser:

1. sends a unique token in Chat A;
2. waits for the first turn to complete;
3. reloads the Odoo web client;
4. reopens the same conversation;
5. asks for the exact prior token;
6. requires the provider answer to recover it;
7. inspects the persisted second-turn context to prove the current question did not leak into its own prior context;
8. creates a fresh conversation and proves the token does not cross scopes.

Because Codex App Server reasoning is ephemeral per product call, recovering the token after reload exercises Odoo-owned continuity rather than relying on a provider thread.
