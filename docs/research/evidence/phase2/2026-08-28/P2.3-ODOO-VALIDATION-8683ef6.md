### P2.3-ODOO-FAILURE

The first focused persistence run correctly exposed a defect: appending a later turn event updated
`last_event_sequence`, and the generic `write()` overlay replaced the already persisted provider
envelope with a host fallback. The observed category changed from expected `provider_capacity` to
`provider_protocol`.

Commit `8683ef6e3e8dd3820fe751f6e7726c9351fa7dfc` repairs the overlay so it synthesizes a fallback only
on an explicit terminal/error transition or when the record has no payload. An unrelated later write
can no longer overwrite a validated terminal envelope.

The standalone full Python collection initially required a harness correction: the dependency-light
host-loop contract imported the real addon package and therefore tried to import Odoo during
collection. It now loads the runtime beneath an isolated package namespace. The HOOT run also made
the authentication precondition explicit in the history-service test; the composed product service
intentionally blocks chat actions until the runtime account is authenticated.

The 36 Python skips are reported, not counted as passes. They belong to retired sidecar/database
integration suites guarded by `ODOO_AI_TEST_DATABASE_URL`, the opt-in real Codex smoke, and explicit
legacy bootstrap/systemd/runtime-install probes. They are not current P2.3 embedded-addon acceptance
gates and do not replace any Phase 2 real-environment validation.

## Scope boundary

This evidence closes only `P2.3-ODOO-UPDATE` and `P2.3-ODOO-FAILURE`. It does not close:

```text
P2-REAL-AUTH
P2-REAL-ACL
P2-REAL-TIMEOUT
P2-REAL-TOOLFAIL
P2-REAL-RECOVERY
```

Those tests require the not-yet-implemented browser consumer/presentation slice so the structured
failure can be observed end to end. Existing HOOT tests for legacy error-code prose do not satisfy
that requirement.
