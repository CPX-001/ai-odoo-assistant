## Objective

Bound P0-D1 without issuing any business write: determine whether the previously observed
`codex-code-mode-host` signal-5 failures can coincide with or cause Odoo service loss/restart.

The original observation remains historical evidence only: Codex 0.149.1 child processes terminated
with signal 5 during the failed ACTION attempt and Odoo subsequently restarted, but causality was
not proven.

## Static process-boundary inspection

Current `addons/odoo_ai_assistant/runtime/agent/codex.py` starts each Codex App Server with
`start_new_session=True` on POSIX. Shutdown escalation targets `os.killpg(self.process.pid, ...)`,
so the intended signal target is the provider process group created for that App Server, not the
Odoo parent process group.

This makes a direct parent-kill mechanism unlikely from the inspected code, but it is not real
runtime proof. The prior Odoo restart also contained an import/startup failure, so P0-D1 remains open
until the real read-only probe is executed.

## Implemented probe

Added `tests/e2e/phase0_provider_crash_probe.py`.

The probe:

- permits only `hello` and `read_partner`, both catalogued read-only scenarios;
- reuses the existing Phase 0 Odoo HTTP capture path;
- runs 1–5 bounded attempts;
- samples `systemctl show` before/after every attempt using only `MainPID`, `NRestarts`,
  `ActiveState`, `SubState`, and `ExecMainStartTimestampMonotonic`;
- reduces journal content to signal-5/SIGTRAP and `codex-code-mode-host` failure counters;
- never writes raw journal lines, prompts, answers, credentials, tool payloads, provider
  stdout/stderr, or private reasoning into the artifact;
- returns exit 2 if Odoo restarts or is unhealthy after an attempt.

No product runtime, capability, ACL, approval, write, recovery, or provider lifecycle behavior was
changed.

## Reproduction procedure

On the real disposable Odoo environment, update/restart from the implementation commit and use the
same normal-user Phase 0 credentials. Start with `hello` so no business capability is required:

```bash
.venv/bin/python tests/e2e/phase0_provider_crash_probe.py \
  --scenario hello \
  --attempts 3 \
  --systemd-unit odoo.service \
  --out /tmp/phase0/p0.3-provider-crash-probe.json
```

If the original failure only appears under capability activity, repeat once with `read_partner` and
the already validated disposable partner fixture. Do not use `write_preview` or any action scenario.

Pass/bounding evidence requires:

- Odoo remains `active/running`;
- `MainPID`, `NRestarts`, and main-start monotonic identity remain stable across attempts;
- no service restart is observed;
- journal access is available so signal-5/code-mode-host counters can be correlated;
- any provider failure is captured as sanitized evidence without a business write.

If Odoo restarts or becomes unhealthy, stop immediately and preserve the sanitized probe artifact;
do not retry ACTION. If the signal-5 event reproduces while Odoo remains stable, that directly
weakens the hypothesis that the child crash itself kills Odoo and allows the service-loss/import
path to be investigated separately.
