## Objective

Provide bounded, deterministic provider fault fixtures for the three Phase 0 failure paths that were previously named but not safely injectable: provider disconnect/EOF, provider timeout, and invalid final provider output.

This slice is measurement/test infrastructure only. It does not change the embedded product runtime, provider lifecycle, capability framework, Odoo authority, ACLs, approvals, writes or recovery.

## Current-code basis

The fixtures target the current embedded contracts rather than the retired sidecar:

- `runtime/account.py` authenticates the executable through App Server `initialize` + `account/read`;
- `runtime/agent/codex.py` starts a fresh App Server for reasoning and fails closed on EOF, read timeout and malformed final JSON;
- `models/turn_queue.py` keeps those provider errors retryable only while no write barrier exists;
- ADR-016 keeps Codex ephemeral and host-authorized; the model/provider never gains direct ORM, shell, SQL or write authority.

The common fake App Server implements only the minimum fixed protocol needed by the current account gate and reasoning client. It never echoes request content and never emits a dynamic tool request.

### EOF

`codex_phase0_eof` passes the account gate with a fixed non-secret fixture account, passes initialize/thread/start/turn start, then exits immediately after acknowledging `turn/start`.

Expected originating code: `codex_process_eof`.

### Timeout

`codex_phase0_timeout` distinguishes the account client from the reasoning client using the existing `clientInfo.name` values. Account initialization remains healthy. Reasoning initialization remains silent, so the current host-owned 5-second startup timeout bounds each failed attempt.

Expected originating code: `codex_read_timeout`.

This deliberately avoids a 120-second silent turn fixture and therefore keeps the Phase 0 trial bounded even with current retry semantics.

### Invalid final output

`codex_phase0_invalid_output` completes a provider turn with a fixed `agentMessage` whose text is `not-json`. It performs no tool call and supplies no business data.

Expected originating code: `codex_answer_invalid`.

## Manifest

`phase0_provider_fault_manifest.json` binds each scenario to its executable, expected terminal `failed` state and expected original error code. It is fixture metadata only; it does not alter the product failure taxonomy.

## Real procedure

Use only the disposable Odoo environment. Record the current value of `odoo_ai_assistant.codex_executable` first and restore it after every fixture.

For each fixture, set the administrative executable override to the absolute executable path in the checked-out repository. No provider credentials are required by the fake fixture and no real account material is copied.

```text
provider_disconnect   -> tests/fixtures/codex_phase0_eof
provider_timeout      -> tests/fixtures/codex_phase0_timeout
invalid_final_output  -> tests/fixtures/codex_phase0_invalid_output
```

Then run the existing normal-user HTTP capture:

```bash
python tests/e2e/phase0_live_capture.py \
  --scenario <scenario> \
  --out /tmp/phase0/<scenario>.json
```

Observe the final browser error/category and rerun/save the capture with `--ui-error-code` only after that UI value was actually observed.

Stop immediately if a business write/approval path appears, Odoo becomes unhealthy or restarts, the fixture executable is not the exact intended absolute path, or the observed original error differs from the manifest.

After each trial restore the previous Codex executable override and confirm normal provider status.

## Exit rule

P0.4 remains `REAL_ENV_VALIDATION_REQUIRED` until all three named fixture paths have real sanitized backend captures and actually observed UI pairs. ACTION remains separate; do not infer a write PASS from fault-fixture results.
