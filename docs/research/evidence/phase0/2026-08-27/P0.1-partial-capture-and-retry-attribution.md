## Objective

Address two Phase 0 measurement defects discovered by the first real Odoo+Codex run without changing provider/runtime architecture:

1. a polling transport/status failure must return a sanitized partial trace instead of raising before the trace can be written;
2. a transient diagnostic failure from an attempt that later recovers must not be promoted to terminal `original_error_code` on a successful turn.

## Changes

`tests/e2e/phase0_live_capture.py` now:

- adds `capture_error_code` as a measurement-tooling error separate from product `request_error_code` / `original_error_code`;
- returns a sanitized partial trace for polling timeout, Odoo HTTP/RPC capture failure, invalid status response or turn-id mismatch after a turn was persisted;
- retains already collected sanitized status snapshots and timings and records a terminal capture-side timing marker;
- keeps `expectation_met=false` for interrupted captures so `phase0_report.py` cannot count them as successful live evidence;
- treats `completed` and `awaiting_confirmation` as non-error terminal states for purposes of `original_error_code`, so recovered transient diagnostic codes remain evidence in events but do not masquerade as terminal failures;
- includes the capture-side error code in the runner's compact console result.

`tests/unit/test_phase0_live_capture.py` adds deterministic regression cases for:

- recovered `codex_turn_failed` diagnostic followed by a completed turn => `original_error_code=None`;
- Odoo transport failure during polling => sanitized partial trace is returned with `capture_error_code=odoo_http_unavailable` and prior snapshots retained.

## Invariants

- No prompts, assistant answers, raw tool/provider payloads, credentials or unrestricted event payloads are persisted.
- Product runtime, Codex adapter, provider lifecycle, ACL/authority and write semantics are unchanged.
- Interrupted captures do not satisfy a real validation gate.
- A capture-tool failure is not mislabeled as a product/provider terminal error.

2. placed a loopback-only HTTP proxy between the capture runner and Odoo;
3. forwarded authentication and `/odoo_ai/v1/turn` unchanged so a real turn and queued event were

- one already observed `queued` snapshot and all available timing points were retained;

- recursive field inspection found no message, password, prompt, answer/response, tool arguments or

- the supplied message and temporary password were absent from the serialized artifact.

The runner exited non-zero because `expectation_met=false`; that is the expected outcome for an
interrupted capture and does not make the validation fail.
