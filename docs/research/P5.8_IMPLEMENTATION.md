## 1. Outcome

P5.8 is implemented as extensions of the accepted P3-P5.7 Odoo-owned runtime. It adds no sidecar, no second tool registry and no model-owned execution/navigation authority.

Current product path:

```text
Odoo durable turn
   |
   +-- correlated semantic activity / readable summary / answer deltas
   +-- durable same-turn interventions + Stop
   +-- CapabilityDefinition execution and write barrier
   +-- explicit HOST-only safe compensation
   +-- host-resolved contextual navigation references
   v
modern Assistant UX while Odoo remains authority
```

The implementation is waiting at validation. No committed automated or real gate is recorded PASS by the GitHub-only implementation work.

## 2. Correlated semantic activity

`CapabilityExecutor` generates host-owned `activity:v1:<32hex>` identifiers and carries the same identifier across one capability lifecycle. Provider reasoning passes use the same pattern, with independent IDs for initial reasoning and post-effect synthesis.

The frontend reducer:

- upserts by `activity_id`, sequence as fallback;
- ignores replay duplicates;
- keeps independent same-capability calls separate;
- derives semantic presentation from trusted phase/status facts;
- computes elapsed duration and semantic step count;
- preserves failure/approval/cancelled states regardless of cosmetic filtering.

Per-user presentation profiles are `compact | normal | detailed | diagnostic`. Technical names are hidden by default. These preferences never alter execution policy.

## 3. Readable reasoning summaries only

Codex App Server `item/reasoning/summaryTextDelta` can enter a dedicated bounded live channel.

Hard privacy boundary:

```text
summaryTextDelta -> bounded readable summary
textDelta        -> ignored / never projected
```

Missing provider summary support falls back to semantic host activity. No private chain-of-thought becomes browser state.

## 4. Same-turn interventions and Stop

P5.8 adds durable `odoo.ai.turn.intervention` rows. Each intervention is bound to copied/validated turn, conversation, user and company identity with:

```text
monotonic sequence
client_intervention_id
bounded message
pending | applied | superseded state
strict count and total-byte budgets
```

The browser persists a correction through Odoo first. It never starts a second ordinary turn merely because the user corrected an active one.

Queued turns consume durable corrections before their first provider decision. Running turns use `InteractiveCodexDecisionEngine`:

```text
Odoo durable correction
 -> if current disposable App Server subturn is alive:
      best-effort turn/steer(threadId, expectedTurnId, input)
 -> otherwise / steer rejected:
      interrupt disposable subturn
      restart NextDecision from Odoo durable correction state
```

The provider process is therefore an optimization for responsiveness, never the persistence source of truth. Provider thread/turn IDs remain inside the host boundary.

Before accepting a decision and before crossing the effect barrier, the host checks that the observed intervention sequence is still current. A later accepted correction invalidates stale provider work.

Stop reuses the existing Odoo `cancel_requested/cancelled` lifecycle and cooperative provider interrupt. The current conversation scope supplies the durable Odoo turn UUID, so another chat remains independent. Partial visible answer text is retained as an Assistant message marked `Interrumpido` instead of disappearing.

## 5. Approval supersession

If a correction arrives while a plan is `awaiting_confirmation`, Odoo does not keep the old approval alive. It records `approval.rejected`, clears the executable old plan/result/working state and requeues the same durable turn with the new intervention.

The old plan can never be executed merely because it had previously reached preview/approval.

## 6. Effect-boundary ordering

Turn controls remain ordered against the accepted P5.5 write barrier. The final control check and barrier acquisition are serialized using the existing host-side advisory effect lock.

Legal race outcomes are:

```text
control wins -> stale effect does not execute
barrier wins -> correction is rejected as turn_effect_already_committed;
                Stop may stop only remaining work
```

P5.8 does not claim that Stop rolls back an already verified business effect.

## 7. Explicit safe compensation

There is no PostgreSQL rollback feature in the Assistant UX. Reversion is a new host-owned compensating operation for effects with explicit safe inverses.

Initial supported operations:

```text
odoo.record.patch       -> odoo.record.patch.revert
odoo.record.archive     -> odoo.record.archive.revert
odoo.record.unarchive   -> odoo.record.unarchive.revert
```

Inverse definitions are ordinary `CapabilityDefinition`s with `HOST` exposure and `INTERNAL_REVERSIBLE` effect. They are not included in the model capability catalog.

The original preview stores only bounded prior state required to compensate. Reversion then:

1. verifies original capability/version/result binding;
2. revalidates current user write authority and record rules with `su=False`;
3. compares current values to the verified post-effect value;
4. refuses a later-user-change conflict;
5. restores only the captured prior fields/state;
6. re-reads and verifies the compensation;
7. records completed reversion only after verification.

The UI offers `Revertir cambios` only for a host-declared available compensator and asks for explicit confirmation. Unavailable/conflicting/unauthorized reversion never reports success.

## 8. Contextual navigation

Supported first-class public reference kinds are now:

```text
odoo_record
odoo_model
odoo_action
odoo_view
odoo_menu
odoo_setting
```

`odoo.resolve_navigation` is a read-only reasoning capability in the existing registry. Its inputs are semantic query text, an optional bounded kind filter and limit. The model does not submit concrete IDs as authority.

The capability searches current Odoo models, window actions, safe views, visible menus and installed `res.config.settings` fields under the effective user. Results contain localized labels/descriptions plus only the minimum typed reference identifiers needed for later revalidation.

Discovery and opening are intentionally separate. A browser click sends the typed reference back to `/odoo_ai/v1/public-references`. Odoo rechecks current existence, user/company access, groups/menu visibility, target-model eligibility and settings schema before returning a closed navigation descriptor. Only that returned descriptor reaches `actionService`.

No model-generated URL or arbitrary route is executable authority.

## 9. Streaming and final-answer references

`PublicTurnEvent` now carries an optional bounded `references` collection separately from existing record `resource` projection. `CapabilityExecutor` only projects navigation references from a schema-valid `odoo.resolve_navigation` result.

References therefore appear as compact chips inside correlated streaming activity.

The host loop also captures validated navigation results into bounded Odoo turn state and adds them as structured `references` beside the final response. The UI renders these directly below the answer area. Prose may say “Puedes encontrarlo aquí”, but the clickable destination remains the structured Odoo reference rather than a Markdown URL.

A revoked/deleted reference fails closed with a discreet notice and never invokes the action service.

## 10. Progressive disclosure and generic record presentation

Record references still use bounded disclosure:

```text
first page: 5 rows by default
show more: next bounded page
show remaining: only inside hard render ceiling
over limit: model/list fallback remains available
```

Eligible OCA/custom business models retain generic schema/access-driven presentation using a small set of current readable fields. This is recomputed at resolution time rather than trusted from provider output.

## 11. Preserved invariants

P5.8 preserves:

- Odoo as persistence/operational/navigation authority;
- effective-user business execution with `su=False`;
- `CapabilityDefinition` as the sole executable capability contract;
- host schema/policy/approval/effect/verification authority;
- write-barrier certainty and no blind retry of ambiguous effects;
- per-conversation turn scopes;
- one authoritative final Assistant response;
- no arbitrary SQL/Python/shell/sudo/Odoo methods;
- no arbitrary browser routes;
- no private chain-of-thought exposure.
