## 1. Outcome

The P5.8 implementation is present as one coherent extension of the accepted P3-P5.7 runtime. It does not add another runtime, another tool registry or any model-owned authority.

Implemented product path:

```text
host/runtime lifecycle facts
        |
        +-- host-generated activity_id correlation
        v
bounded public live events
        |
        +-- semantic reducer/upsert
        +-- readable reasoning-summary channel
        +-- safe typed resource references
        v
compact live headline
+ expandable semantic activity
+ progressive record disclosure
+ optional technical/diagnostic detail
```

The implementation is intentionally waiting at the validation boundary. No deterministic, Odoo, HOOT or real gate is recorded PASS merely because its test is committed.

## 2. P5.8a — correlation + semantic reducer

`CapabilityExecutor` generates host-owned `activity:v1:<32hex>` identifiers and carries the same identifier across one capability's start/completion/failure lifecycle. Independent calls always receive independent identities.

The current ADR-019 host loop now applies the same rule to provider reasoning passes. The initial reasoning pass and post-effect synthesis each receive a different activity ID; completion or failure closes the same semantic item. This removes the former possibility of a provider activity remaining permanently `running` in the semantic UI.

The frontend reducer:

- upserts by `activity_id` and uses event sequence only as a fallback;
- ignores replay duplicates by sequence;
- keeps independent same-capability operations separate;
- computes a semantic code from trusted phase/status facts;
- derives completed duration and semantic step count;
- keeps failure/approval states visible regardless of cosmetic filtering.

## 3. P5.8b — presentation profiles, localization and bounds

Per-user Odoo-owned presentation preferences now cover:

```text
activity_detail_level = compact | normal | detailed | diagnostic
activity_transient_threshold_ms = 1200 by default
activity_batch_page_size = 5 by default
activity_show_technical_names
activity_show_step_durations
activity_reasoning_summary = off | concise | detailed
```

Server ceilings bound activity items, batch rows and reasoning-summary characters. These settings affect presentation only; they cannot alter ACLs, capability availability, approval, execution or audit persistence.

Deterministic semantic wording is rendered through Odoo translation semantics (`_t` in OWL and translatable XML literals). Technical identifiers remain stable and are hidden by default.

## 4. P5.8c — readable reasoning summaries only

Codex App Server `item/reasoning/summaryTextDelta` is accepted through a dedicated bounded live channel. It is optional presentation data and never becomes business authority.

Hard privacy boundary:

```text
summaryTextDelta -> bounded public reasoning-summary channel
textDelta        -> deliberately ignored / never projected
```

The stream is bounded per delta and per turn, correlated by provider item/summary index, replay-safe in the frontend and isolated by active turn scope. A provider that does not emit readable summaries simply falls back to semantic host activity; unsupported summary support is not a product failure.

## 5. P5.8d — typed Odoo references and generic presentation

Current first-class safe reference kinds are the ones the existing product can ground without Phase-8 intelligence:

```text
odoo_record
odoo_model
```

The browser never opens a model-generated arbitrary route. It submits a closed typed descriptor to Odoo; the host revalidates model eligibility, current record existence and current read access immediately before returning a navigation descriptor. Revoked/deleted references fail closed.

Capability completion may project only already schema-validated record identities. The host then re-reads those IDs under the same effective user before adding bounded display names. Query results, single-record mutation results and bounded record-id result lists use the same projection seam.

Unknown OCA/custom models receive a generic presentation from current effective schema/field metadata and at most three currently readable safe fields. The implementation deliberately performs fresh schema/access inference on each reference resolution rather than caching a model-generated presentation spec. This is a conscious simplification from the target document: it avoids coupling browser navigation to an extra provider call and automatically survives schema/ACL changes by revalidation. A later trusted optional presenter/refinement hook can extend this seam without changing reference authority.

Action/view/menu/setting/source/web/document reference kinds remain extensibility targets for the phases that can actually ground those entities. P5.8 does not invent Phase-8 source/view/menu intelligence merely to populate the type list.

## 6. Progressive disclosure

Record references are rendered with bounded progressive disclosure:

```text
first page: 5 rows by default
show more: next bounded page
show remaining: only while within configured browser row ceiling
over limit: expansion remains blocked and an Odoo model/list navigation fallback is offered
```

This is presentation backpressure only. It never limits the underlying business operation or changes execution authority.

## 7. Preserved invariants

P5.8 preserves:

- Odoo as persistence and operational authority;
- effective-user business execution with `su=False`;
- `CapabilityDefinition` as atomic executable authority;
- host validation of schema/policy/approval/effects/verification;
- P5.5 write barrier and post-effect certainty;
- P5.6/P5.7 turn context/settings immutability;
- one authoritative final Assistant message;
- public activity, answer deltas and reasoning summaries as separate presentation channels;
- no arbitrary SQL/Python/shell/Odoo method or browser-route authority;
- no private chain-of-thought exposure.
