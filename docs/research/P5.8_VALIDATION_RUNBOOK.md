# P5.8 semantic activity/reasoning/navigation UX validation runbook

Date: 2026-08-30  
Status: implementation present; validation required

P5.8 is implemented as one coherent product/interaction slice. It is **not COMPLETE** until the local regression battery and the applicable real Odoo/Codex/Chromium gates below are executed and reviewed on a materially unchanged checkpoint.

## 1. Scope

The implementation under validation covers:

```text
host-generated activity_id correlation across running/completed/failed lifecycle rows
semantic reducer/upsert and compact live headline
completed duration + semantic step count
compact / normal / detailed / diagnostic presentation profiles
bounded transient-step filtering and render limits
provider-declared readable reasoning summaries on a separate live channel
raw/private reasoning rejection
per-user activity presentation preferences
typed Odoo record/model references with fresh ACL revalidation before navigation
generic schema/access-driven record presentation
progressive record disclosure with list-view fallback
Odoo-localized deterministic semantic labels
current-chat Stop with provider interruption and durable cancellation
same-turn ordered redirect while queued/running or awaiting approval
stale provider decision rejection before the write barrier
transaction-scoped advisory serialization of Stop/redirect versus write-barrier commit
visible interrupted partial answer
host-only explicit compensation for safely reversible verified effects
conflict-safe patch/archive reversion with post-write verification
```

Interactive control does not make the browser or provider an authority surface. Odoo owns the durable control state; effect compensation uses existing host capability validation and the effective Odoo user. The advisory lock is only a narrow ordering primitive around the final control/effect boundary and grants no additional authority. Phase-6 multi-step EffectPlan semantics remain out of scope.

## 4. Real HARD gates

Run the following observations on the same implementation lineage. A runner may combine several observations, but evidence must retain each validation ID separately.

### `P5-REAL-SEMANTIC-ACTIVITY`

A real read-only turn and a real effectful turn must show the latest meaningful semantic activity in the collapsed header, avoid duplicated started/completed rows and settle to a completed duration + semantic step count without changing the authoritative final answer.

### `P5-REAL-ACTIVITY-DEDUPE`

Exercise repeated calls to the same capability and require two independent semantic items while each individual started/completed or started/failed lifecycle collapses to one item.

### `P5-REAL-REASONING-SUMMARY`

With a Codex build/model that emits readable `item/reasoning/summaryTextDelta`, require bounded summary text through the dedicated reasoning channel. Confirm `item/reasoning/textDelta` is never projected to browser state. If the provider emits no readable summaries, record the unsupported-provider observation; fallback activity must remain correct and private reasoning must remain absent.

### `P5-REAL-ACTIVITY-I18N`

Run equivalent turns with Spanish and English Odoo users. Deterministic semantic labels and controls must follow Odoo language while capability/model technical identifiers remain unchanged in diagnostic/developer detail.

### `P5-REAL-NAVIGATION-REFS`

Produce a real Odoo record reference from a capability result, open it through the activity UI and verify the host revalidates current access immediately before navigation. Revoke access or remove the record and require fail-closed behavior without an arbitrary browser route.

### `P5-REAL-BATCH-DISCLOSURE`

Exercise a bounded multi-record read/result. Require five visible rows initially, stable `show more` order, a hard rendering limit and an Odoo list/model navigation fallback when expansion would exceed the configured browser bound.

### `P5-REAL-ACTIVITY-RECONNECT`

Reconnect/reload while semantic activity is running. Replayed live events must not duplicate work items, reasoning summary fragments or final Assistant prose; ordering and correlation must remain stable.

### `P5-REAL-TURN-STOP-REDIRECT`

Exercise a real long-running Codex turn. With an empty composer the action button must become Stop; pressing it must interrupt only that chat, normally become observable in under one second, preserve already visible prose marked `Interrumpido`, and leave a simultaneously running second conversation untouched. In another run, send at least two corrections while processing and require them to be applied in order to the same Odoo turn UUID. Repeat from `awaiting_confirmation`: the pending proposal must be superseded without creating a new turn, and the new instruction must drive fresh reasoning. No stale plan may cross the write barrier after a later redirect.

### `P5-REAL-TURN-EFFECT-BOUNDARY-RACE`

Stress the narrow final race between browser control and the first effect. Use a disposable reversible write target and repeatedly release a redirect or Stop at the point an authorized plan is about to cross the write barrier. Only two orderings are valid:

```text
control wins first -> redirect/Stop is durably accepted; the stale plan must not execute
write barrier wins first -> the effect may execute; a redirect must fail with turn_effect_already_committed and Stop may only stop remaining post-effect work
```

Require **zero** observations where a redirect is reported accepted and the older plan nevertheless executes. Also require zero deadlocks, duplicate control sequences or cross-chat effects. Record the iteration count and both observed winner classes. The transaction-scoped advisory lock must be held only across the final control check and barrier commit, not across provider reasoning or business execution.

### `P5-REAL-TURN-REVERSION`

Complete a reversible `odoo.record.patch` or `odoo.record.archive` through the normal effect lifecycle. The completed action summary must expose `Revertir cambios`; executing it must run under the same effective user, restore the verified previous state and verify the compensation. Then mutate the record after the original action and require the same reversion attempt to fail closed without overwriting the later change. A completed effect without an installed safe compensator must explicitly show that automatic reversion is unavailable rather than inventing a rollback.

## 5. Acceptance rules

All P5.8 HARD contracts are host/browser product contracts consumed by Phase 6, so failures block P6 consumption until repaired. No gate is PASS merely because its test exists.

Record for every executed gate:

```text
validation id
exact tested SHA
environment versions
actual selected-test/assertion totals
PASS | FAIL | BLOCKED
bounded sanitized observations
repairs made, if any
```

Do not store credentials, raw prompts/answers, private reasoning, provider stdout/stderr, policy payloads or customer data.
