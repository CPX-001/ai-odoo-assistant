Date: 2026-08-30
Status: `IN_PROGRESS` — semantic work-item repair required before real acceptance

P5.8 has substantial code and automated coverage in the repository. The deterministic/full-addon/HOOT battery passed on checkpoint `0b0ac2d2c8fb25523c2e6e9c3808d3c702cede80`, but a current product review identified a remaining P5.8 semantic-activity gap: normal-user activity can still resemble a technical capability lifecycle log instead of the coherent semantic work-item UX required by `P5.8_SEMANTIC_ACTIVITY_UX.md`.

Therefore the existing automated PASS evidence is preserved, but **P5.8 is not ready to be accepted as-is**. Repair the semantic work-item projection, rerun the affected automated gates on the repaired candidate, then execute the full real-environment chain below.

## 1. Scope under validation

The P5.8 scope covers:

```text
coherent semantic work items above raw lifecycle events
bounded readable reasoning summaries (never private reasoning)
structured answer streaming
current-chat Stop
ordered same-turn durable interventions/corrections
best-effort live Codex turn/steer with durable Odoo fallback

record/model/action/view/menu/setting references
fresh Odoo revalidation before every navigation

```

Interactive turn control and contextual navigation are independent contracts. Neither grants browser/model business authority.

## 3. Mandatory semantic repair before acceptance

### Known mismatch

The target specification says the Assistant must not expose a chronological dump of technical capability lifecycle events. A representative observed flow still looked like:

```text
Procesando petición
Analizando petición
Inspect Odoo write schema · sale.order
Inspect Odoo write schema · sale.order
Inspect Odoo query schema · res.partner
Inspect Odoo query schema · res.partner
Query Odoo records · res.partner
Query Odoo records · res.partner
Respuesta preparada
Mutate multiple Odoo records · sale.order
Mutate multiple Odoo records · sale.order
Mutate multiple Odoo records · sale.order
Ejecutando acción autorizada
Mutate multiple Odoo records · sale.order
La petición requiere revisión
```

That is a **P5.8 failure**, not acceptable normal-mode output and not Phase 6 work.

### Required repaired behavior

Normal mode must project lifecycle/runtime facts into a small number of meaningful host-owned work items. The implementation does not have to use a particular class name or copy exact strings, but it must provide enough structured semantics to support behavior equivalent to:

```text
Analizando la petición
Preparando 200 presupuestos demo
  Consultando clientes existentes
Creando presupuestos
  50 / 200
  100 / 200
  150 / 200
  200 / 200
Verificando resultados
  200 presupuestos creados
```

Only show progress/counts that are grounded in host-known facts. Never invent percentages or completed counts from model prose.

A valid implementation may use the target's conceptual fields such as:

```text
activity_id
parent_activity_id / semantic_group_key
category / operation
headline_code + bounded headline_args
status
progress {current,total} when known
result_summary when verified/known
references[]
```

or a simpler equivalent contract. The important product requirement is that normal mode is semantic and coherent while diagnostic mode may retain technical lifecycle detail.

### Required deterministic regression coverage

Before real gates, add or strengthen tests proving at least:

- one capability lifecycle `started -> completed` becomes one visible semantic work item;
- related repeated child operations can be grouped only with explicit host-owned semantic correlation/grouping, never string equality alone;
- normal mode does not expose raw capability titles such as `Inspect Odoo write schema`, `Query Odoo records` or `Mutate multiple Odoo records` as the primary user-facing rows;
- diagnostic mode may expose technical capability/model detail without private reasoning;
- semantic labels use codes/arguments and Odoo translation, not protocol identity based on Spanish/English literals;
- grounded batch progress/result counts are rendered when available and omitted when not available;
- approval/failure/partial/cancelled states remain first-class and are never hidden by grouping.

This repair is the immediate P5.8 implementation work. Do not start Phase 6 or run the final real acceptance chain against a candidate known to violate it.

## 5. `P5-REAL-SEMANTIC-ACTIVITY`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED` after the semantic repair and green automated battery.

### Preconditions

- exact repaired candidate SHA installed;
- normal activity detail level enabled;
- technical names disabled;
- at least one read-heavy turn and one approval/write-oriented turn long enough to expose multiple capabilities;
- use only disposable business data for any effect scenario.

### Representative scenarios

Run at least:

1. a read-oriented prompt that needs schema discovery plus multiple Odoo reads;
2. an approval-oriented prompt comparable to `¿puedes crear 200 presupuestos demo?` where the Assistant must inspect schema/data and prepare a bounded action/plan. Do not approve destructive or unsuitable test work merely to force the scenario; the pre-approval activity is already relevant.
3. where safe and supported, a bounded disposable batch that reaches execution/verification so grounded progress/result summaries can be observed.

### Expected normal-mode UI

- one lifecycle operation appears as one evolving work item, not duplicated start/completion rows;
- the activity log communicates **what the Assistant is doing in business/user terms**, not just which capability function is executing;
- related child operations are grouped when host-owned semantic correlation says they belong together;
- independent operations remain independent even when they use the same capability;
- raw technical titles such as `Inspect Odoo write schema`, `Inspect Odoo query schema`, `Query Odoo records`, `Mutate multiple Odoo records` are not the primary normal-mode rows;
- model names such as `sale.order`/`res.partner` are hidden by default unless they materially aid understanding through a human label/reference;
- live headline follows the latest meaningful semantic item;
- approval remains visible/actionable outside the reasoning disclosure;
- completion collapses to a discreet duration + semantic step count;
- partial/failure states remain understandable rather than disappearing into generic `Trabajando en Odoo` labels.

### Expected backend/product contract

- lifecycle/audit events remain intact internally;
- semantic grouping uses host-owned identities/keys, never textual equality of model output;
- any progress/result count is grounded in validated host capability/verification data;
- provider readable summary may add bounded context but cannot define execution state or fabricate progress;
- private/raw reasoning is absent.

### Hard failure conditions

Any of these is a FAIL:

```text
normal mode is still primarily a chronological capability lifecycle dump
one operation visibly appears twice solely as started/completed rows
several related batch calls flood the user with repeated raw tool titles
technical CapabilityDefinition.title strings dominate normal mode
normal mode cannot distinguish meaningful business work beyond generic phase labels
progress/result counts are invented from model prose rather than host-known facts
private/raw reasoning appears
```

A failure here creates one coherent P5.8 semantic-activity repair slice. Do not split each label, capability or frontend/backend symptom into separate micro-slices unless a real gate/authority boundary requires it.

### Evidence required

Exact SHA, sanitized screenshot/observation for the read scenario and approval/batch scenario, number of raw public lifecycle events vs visible semantic work items, visible labels/grouping, any grounded progress/result summary, detail-level setting and confirmation that raw technical titles/private reasoning are absent from normal mode.

## 11. `P5-REAL-NAVIGATION-REFS`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED`.

### Preconditions

- exact candidate SHA installed;
- normal non-admin internal user with readable business records;
- at least one record/model reference naturally produced by the Assistant;
- browser action service functioning normally.

### Steps

1. Ask a read-only question that causes a grounded record result.
2. Confirm a compact record/model reference appears in semantic activity or result presentation.
3. Open the reference.
4. Confirm the browser first calls `/odoo_ai/v1/public-references` with the typed reference, then navigates using the returned closed descriptor.
5. Repeat after deleting the target or revoking current read access.

### Expected backend result

- record/model is re-read under the effective user with `su=False`;
- current existence/ACL/record rules are checked;
- valid target returns a closed `record` or `model` navigation descriptor;
- revoked/deleted target returns `reference_unavailable`.

### Expected UI result

- valid target opens the expected Odoo form/list;
- technical IDs are not the default visible label;
- revoked target shows a discreet unavailable notice and does not navigate.

### Security checks

- no model-authored URL/route reaches `actionService`;
- user/company context is unchanged;
- no sudo business read is introduced.

### Cleanup

Restore the ACL/rule or recreate the disposable record if changed.

### Evidence required

Exact SHA, user role (sanitized), reference kind, successful navigation observation, revoked/deleted fail-closed observation and absence of arbitrary route execution.

- menus come from current Odoo visibility;

### Security checks

- extra keys/raw routes are rejected;
- no arbitrary `ir.actions.*`/view/menu ID supplied by model text is executed;
- company/group visibility is respected.

### Cleanup

One sanitized observation for each available kind, one settings resolution, one revoked visibility failure and exact SHA/environment versions.

## 14. `P5-REAL-TURN-STOP`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED`.

### Preconditions

- two separate Assistant conversations available;
- one real Codex turn long enough to interact with;
- answer streaming visible.

### Steps

1. Start a long-running turn in Chat A and another independent turn in Chat B if capacity permits.
2. Return to A with an empty composer.
3. Confirm the action becomes the square Stop control with title/aria-label `Detener respuesta` while textarea remains editable.
4. Allow some provisional prose to appear when possible, then press Stop.
5. Observe immediate Odoo state transition to `cancel_requested` or terminal `cancelled` and eventual provider interruption.
6. Verify B continues unaffected.

### Expected backend result

- only A's durable turn UUID is sent to `/odoo_ai/v1/turn/cancel`;
- Odoo records cancellation before depending on provider interruption;
- a live Codex subturn receives best-effort `turn/interrupt` targeting its current `(threadId, turnId)`;
- no stale final answer from A becomes authoritative after accepted cancellation.

### Expected UI result

- Stop normally becomes observable in under one second;
- partial visible prose is retained as an Assistant message marked `Interrumpido`;
- B retains its own running/completed state.

### Security checks

- no Codex thread/turn IDs reach the browser;
- Stop cannot roll back an effect already across the durable write barrier;
- post-effect verified actions remain clearly listed if processing is stopped afterward.

### Cleanup

Remove disposable test records/conversations if the environment policy requires it.

### Evidence required

Exact SHA, A/B turn states, measured Stop observation latency, interrupted-fragment behavior and proof B was not cancelled.

## 15. `P5-REAL-TURN-INTERVENTIONS`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED`.

### Preconditions

- a long-running real Codex turn;
- ability to observe the same Odoo turn UUID throughout;
- a separate approval-required scenario.

### Steps

1. Start a turn and, while it is queued if practical, type a correction and submit it.
2. Confirm the textarea was writable and the action label became `Corregir instrucción`.
3. Verify the draft clears only after Odoo acknowledges the durable intervention.
4. While running, submit at least two further corrections in order.
5. Repeat the same `client_intervention_id` against the same turn in a controlled request and confirm no duplicate durable row/message is created; conflicting content with that id must fail closed.
6. Confirm a live steerable Codex subturn receives `turn/steer` with `expectedTurnId`; where steering is unavailable, confirm the ephemeral subturn is interrupted/restarted from durable Odoo state rather than losing the correction.
7. Create an approval-required plan, then send a new instruction instead of approving it.
8. Confirm the pending plan is explicitly rejected/superseded, the same Odoo turn resumes/requeues, and the old plan never executes.

### Expected backend result

- interventions are monotonic/durable on one `odoo.ai.turn`;
- user/company/conversation/turn bindings remain exact;
- max count/byte budgets are enforced;
- `client_intervention_id` provides idempotent duplicate protection;
- queued interventions are consumed before first provider decision;
- running interventions are persisted before any steer attempt;
- host checks redirect sequence again before the write barrier.

### Expected UI result

- no second ordinary turn is created for a correction;
- corrections appear in user-message order;
- another conversation remains independent;
- approval card disappears only because the old plan was explicitly superseded.

### Security checks

- provider steer is advisory transport, not durable authority;
- browser never receives provider IDs;
- a correction cannot bypass capability policy/approval/ACL/verification;
- stale old plan cannot cross the write barrier after a later accepted correction.

### Cleanup

Reject/cancel any remaining disposable plan and restore modified records.

### Evidence required

Same Odoo turn UUID, ordered intervention sequences/client IDs, duplicate/conflict behavior, steer-or-fallback observation, approval rejection event and absence of stale-plan effects.

## 16. `P5-REAL-TURN-EFFECT-BOUNDARY-RACE`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED`.

Stress the narrow race between browser control and first effect using a disposable reversible target.

Valid orderings only:

```text
control wins -> accepted control is durable and stale plan does not execute
barrier wins -> effect may execute; redirect returns turn_effect_already_committed and Stop affects only remaining work
```

Require zero observations where a redirect is reported accepted and the older plan nevertheless executes, zero deadlocks and zero cross-chat effects. Record iteration count and observed winner classes. The advisory lock must be held only for the final control check/write-barrier ordering, not across provider/business work.

## 17. `P5-REAL-COMPENSATION`

Status before execution: `REAL_ENV_VALIDATION_REQUIRED`.

### Preconditions

- disposable records writable by the selected effective user;
- normal approval/effect flow available;
- targets suitable for patch, archive and unarchive.

### Steps

1. Execute and verify an `odoo.record.patch` through the normal plan lifecycle.
2. Confirm performed-actions UI offers `Revertir cambios` only after host marks compensation `available`.
3. Press Revertir, confirm the explicit confirmation UI, then execute it.
4. Verify previous bounded field values are restored and re-read before UI says reverted.
5. Repeat for archive and unarchive where supported.
6. Execute another patch, then modify the affected field afterward through another user/action; attempt reversion and require optimistic-conflict failure without overwriting the newer value.
7. Revoke write permission/record-rule access after the original effect and attempt reversion; require fail-closed behavior.
8. Complete an effect without a safe installed compensator and verify UI says automatic reversion is unavailable.

### Expected backend result

- original preview stores only bounded prior values needed by the explicit compensator;
- compensation capability is HOST-only and never model-callable;
- current ACL/record rules are revalidated under `su=False`;
- current value must still match the verified post-effect value before restoring old data;
- restoration is written and then verified;
- result state changes to completed only after verification.

### Expected UI result

- performed actions remain visible;
- Revertir is shown only when the host declares safe compensation;
- explicit user confirmation is required;
- conflict/permission failures do not claim reversal;
- verified reversal changes card state to `Cambios revertidos`.

### Security checks

- no PostgreSQL rollback claim;
- no arbitrary inverse method execution;
- later user modifications are never overwritten;
- unavailable compensation is reported rather than invented.

### Cleanup

Restore/discard all disposable records and temporary rules/groups. Confirm no temporary access rule remains active.

### Evidence required

Patch + archive/unarchive observations, before/effected/reverted values, conflict case, permission-revocation case, unavailable-compensator case, verification result and exact SHA.
