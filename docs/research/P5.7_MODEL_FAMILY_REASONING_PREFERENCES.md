# P5.7 — Model-family picker and reasoning-effort preference

Date: 2026-08-29  
Status: **ACCEPTED SUB-SLICE on checkpoint `eb66e45`**
Owning roadmap slice: `P5.7-conversation-scoped-preferences`  
Scope note: this is one coherent P5.7 product sub-slice. It does **not** by itself complete the broader conversation-scoped preference-mutation contract.

## 1. Product behavior

The composer now treats model family, model variant and reasoning effort as separate concepts.

Target normal-user presentation:

```text
Modelo
  GPT-5.6  >
             Sol
             Terra
             Luna

Razonamiento
  Predeterminado
  Ninguno
  Mínimo
  Bajo
  Medio
  Alto
```

The provider remains the authority for supported efforts. The normal compact picker intersects that catalog with the product-facing range from `none` through `high`; deeper provider-only levels are not offered in this surface. Unknown/future models remain selectable without requiring a core-code family table; they simply appear as an ungrouped model until trusted presentation metadata can describe them better.

For families following the current provider naming convention `gpt-X.Y-sol|terra|luna`, the UI groups the returned provider model ids under one `GPT-X.Y` family. If App Server also returns the bare family alias together with an explicit Sol entry, the presentation layer avoids showing Sol twice. This is UI grouping only: the host still persists and sends the exact provider model id selected by the user.

Nested Odoo `Dropdown` composition is used for variant selection. Odoo's dropdown component provides the desired hover-open behavior for child menus while preserving click/focus/keyboard/touch interaction; the product therefore does not depend on hover alone.

## 2. Reasoning-effort authority

Reasoning effort is a user preference for future turns, not a live mutation of an already queued/running turn.

Flow:

```text
Codex model/list
  -> supportedReasoningEfforts + defaultReasoningEffort
  -> bounded host validation
  -> browser picker
  -> user selects explicit effort or Predeterminado
  -> Odoo-owned user preference
  -> immutable per-turn settings snapshot
  -> CodexAgentSettings.reasoning_effort
  -> App Server thread/start config.model_reasoning_effort
```

`Predeterminado` stores no explicit effort. In that case the Assistant lets the provider/model use its advertised/default behavior rather than synthesizing a fake value.

An explicit effort is accepted only if the currently effective model advertises it. Changing model revalidates the stored effort; an incompatible explicit effort is cleared rather than silently forcing an unsupported setting.

An intelligent host-owned `Auto` reasoning mode is deliberately **not** implemented in this slice. Phase 6 adaptive/deliberate strategy is the better place to decide reasoning depth from measured task complexity and evals.

## 3. Turn immutability

The execution-settings checkpoint is promoted from format v1 to v2:

```text
format_version: 2
reasoning_model
reasoning_effort
autonomy_profile
policy
```

Existing v1 checkpoints remain readable. New turns capture the current user reasoning-effort preference at creation time. After capture, `reasoning_model`, `reasoning_effort`, `policy_payload` and `execution_settings_payload` are immutable for that turn.

Therefore:

```text
Turn A: GPT-5.6 / high
user changes picker -> GPT-5.6 Terra / low
Turn A continues: original model / high
future Turn B: selected Terra / low
```

Revocable Odoo ACLs, record rules, capability availability and provider health remain dynamic; this snapshot does not authorize anything.

## 4. Provider boundary

The active ADR-019 path uses `StreamingCodexDecisionEngine`. Both the active streaming adapter and the non-streaming/base Codex decision adapter now pass an explicit captured effort as the App Server thread configuration:

```text
config.model_reasoning_effort = <captured effort>
```

The older `CodexReasoningEngine` compatibility path uses the same setting. No provider-side tool or authority changes were introduced.

## 5. Localization

Deterministic user-visible wording is localized through Odoo:

- QWeb/XML literals remain translation-extractable;
- JavaScript dynamic labels/descriptions use `_t(...)`;
- protocol tokens such as `medium`, `xhigh`, exact model ids and `model_reasoning_effort` remain stable technical identities and are not translated;
- Sol/Terra/Luna are product/model names, not locale-specific protocol labels.

This follows the product-wide rule that deterministic Assistant UX must render in the effective Odoo language instead of embedding Spanish protocol strings.

## 9. Loading-state interaction repair

Real Chromium validation after acceptance exposed a short startup interval in which the model catalog was still loading. The custom model and reasoning trigger buttons looked enabled, but their parent Odoo `Dropdown` components were disabled and silently ignored clicks. The autonomy picker did not depend on that catalog, which is why it continued to work.

Checkpoint `4e72c5c` keeps both pickers openable during catalog loading, renders an explicit loading state inside each menu, and exposes a bounded retry action if the catalog cannot be loaded. Only an in-flight preference save disables its native trigger. The P5.3 browser gate now asserts that both pickers actually open, and a source contract protects the loading/retry behavior. Real-browser, focused and full-HOOT evidence is recorded in `evidence/phase5/2026-08-29/P5.7-DROPDOWN-LOADING-REGRESSION-4e72c5c.md`.

## 10. Compact composer controls

The model, reasoning and autonomy selectors use small pills in the composer so preference labels do not consume chat space. The closed state uses a bounded token or established Font Awesome icon, while the open menu retains full localized names and explanatory copy. Model selection uses a subtle row background instead of check icons; grouped families rely on the single dropdown arrow supplied by Odoo. The visible reasoning range ends at `high` even if the provider advertises deeper internal levels.
