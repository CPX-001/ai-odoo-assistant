# P5.5 post-effect reasoning validation runbook

Date: 2026-08-29  
Status: focused HARD Odoo gate required

P5.5 changes the effectful-turn completion path, so acceptance is intentionally ordered from a focused deterministic Odoo gate to broader regression and finally the real provider/product path.

## 1. Exact lineage

Pull current `main`, require a clean worktree, record the exact SHA and update `odoo_ai_assistant` on a disposable Odoo 18 Community database. This slice bumps the addon to `18.0.10.15.0`.

Implementation lineage begins after accepted P5.4 `69041fd0f93bd064d924c7a4440e6bd9b2b11577` and includes the post-effect boundary, host-loop continuation, focused tests and receipt hardening.

## 2. First blocking gate — `P5.5-ODOO-POST-EFFECT`

This is the immediate HARD gate. Run it before the full addon regression or any real provider/browser gate:

```bash
"$ODOO_BIN" -c "$ODOO_CONF" -d "$ODOO_AI_P5_DB" \
  --addons-path="$ODOO_AI_ADDONS_PATH" \
  -u odoo_ai_assistant \
  --test-enable \
  --test-tags '/odoo_ai_assistant:TestPostEffectReasoning' \
  --stop-after-init --log-level=test
```

Required observations:

```text
verified receipt contains bounded authoritative result + verification context
post-effect provider receives zero PLAN capabilities
attempted repeated PlanStepProposal is rejected host-side
rejected repeat proposal performs no write
the same continuation can then produce a natural FinalAnswer
working transcript terminates in one final_answer
```

Acceptance requires a positive selected-test count and `0 failed / 0 errors`.

If this gate fails, stop. Repair only the smallest responsible P5.5 layer and rerun it. Do not start P5.6 and do not spend provider/browser time while this contract is red.

## 4. Real HARD gate — `P5-REAL-POST-EFFECT`

After deterministic acceptance, exercise a real current embedded-runtime action through Odoo + authenticated Codex on a disposable record. Use an existing bounded action capability such as the P5.4 approval fixture; do not add generic method execution for the test.

The real gate must prove:

```text
one effect is proposed and, when required, approved
no business write occurs before approval
execution occurs once
verification succeeds
provider continuation receives the verified outcome
final Assistant prose is natural/provider-produced rather than _completion_answer host prose
no second effect is proposed/executed after verification
the completed browser plan/receipt still reflects the verified action
```

A provider failure after verification must not trigger a blind replay of the effect. If the final synthesis cannot be completed safely, retain existing write-barrier/recovery semantics rather than fabricating success.

The runner/evidence harness for this real gate may be added after the focused Odoo gate is green; it is not necessary to create browser/provider machinery on an unvalidated runtime contract.


Record exact tested SHA, actual totals, Odoo/Python/PostgreSQL versions and Codex/browser versions for the real gate. Do not store credentials, raw provider output, hidden reasoning or customer data.
