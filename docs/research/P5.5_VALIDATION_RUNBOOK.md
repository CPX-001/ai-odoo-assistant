# P5.5 post-effect reasoning validation runbook

Date: 2026-08-29  
Status: accepted on `8427c8849b1e1f3afa6337de1209a6027410c266`

P5.5 changes the effectful-turn completion path. Formal acceptance still preserves causal ordering:

```text
focused post-effect contract
  -> deterministic/full regression
      -> real provider/browser post-effect path
```

The validation is intentionally packaged as one useful batch. A passing sub-gate does not require a manual stop; the batch continues until a genuine failure or the final evidence-review boundary.

## 1. Exact lineage and safety boundary

Pull current `main`, require a clean worktree, record the exact SHA and update `odoo_ai_assistant` on a disposable Odoo 18 Community database. P5.5 production behavior is the verified-receipt continuation described in `P5.5_POST_EFFECT_REASONING.md`.

Required environment:

```text
ODOO_BIN
ODOO_CONF
ODOO_AI_ADDONS_PATH
ODOO_AI_P5_BASE_URL
ODOO_AI_P5_DB
ODOO_AI_P5_LOGIN
ODOO_AI_P5_PASSWORD
ODOO_AI_P5_APPROVAL_ACTION_ID
```

`ODOO_AI_P5_DB` must start with `odoo_ai_`. The managed real gate only starts Odoo on an HTTP loopback origin. `ODOO_AI_P5_APPROVAL_ACTION_ID` must identify a `res.partner` form action usable by the validation user. The browser runner creates and cleans its own disposable partner fixture.

If the Odoo config routes test logs away from stdout, use `ODOO_AI_P55_ODOO_TEST_ARGS` to expose the real Odoo result summary. Optional server overrides may be supplied through `ODOO_AI_P55_ODOO_SERVER_ARGS`.

Stop the normal Odoo service on the validation port, then run the whole remaining P5.5 chain in one command:

```bash
cd "$REPO"
python tests/e2e/p5_5_acceptance_batch.py \
  --summary-out /tmp/p5_5_acceptance.json
```

The batch performs:

```text
clean exact-SHA preflight
```

If all executable checks succeed, the batch returns:

```text

```

That is not formal roadmap PASS. Review the bounded browser observation and exact tested SHA before recording evidence and moving the cursor.

## 3. Focused HARD gate — `P5.5-ODOO-POST-EFFECT`

The batch executes this first:

```bash
"$ODOO_BIN" -c "$ODOO_CONF" -d "$ODOO_AI_P5_DB" \
  --addons-path="$ODOO_AI_ADDONS_PATH" \
  -u odoo_ai_assistant \
  --test-enable \
  --test-tags '/odoo_ai_assistant:TestPostEffectReasoning' \
  --stop-after-init --log-level=test
```

Required deterministic observations now include:

```text
verified receipt retains authoritative result + verification context
oversized receipt degrades to bounded compact verified context
post-effect provider cannot be called without a verified receipt
post-effect provider sees zero PLAN capabilities
attempted repeat PlanStepProposal is rejected host-side and performs no write
continuation can still produce one natural FinalAnswer
provider failure after verification carries effect_state=confirmed
working transcript terminates in one final_answer
```

Acceptance requires a positive selected-test count and `0 failed / 0 errors`.

## 5. Real HARD gate — `P5-REAL-POST-EFFECT`

The prepared runner is:

```bash
node tests/e2e/p5_5_post_effect_browser.mjs \
  --gate P5-REAL-POST-EFFECT
```

Machine-readable gate definition:

```text
tests/e2e/p5_5_real_gates.json
```

The real runner uses the current Odoo-native `odoo.record.patch` capability against a partner record created by the runner itself. It deliberately forces approval with the strict autonomy profile and requests a per-run final marker that only the provider continuation can place in the post-effect `final_answer` transcript item.

Required observations:

```text
exactly one patch proposal reaches awaiting_confirmation
no business write occurs before approval
approval stays bound to the same persisted turn
execution crosses the durable write barrier
one effect executes and verifies
completed plan retains exactly one verified step
durable transcript contains exactly one verified_effect_receipt
one final_answer is appended after that receipt
final answer contains the per-run provider marker
final answer is not the old deterministic _completion_answer text
no plan_step_proposed enters the executable transcript after verification
any attempted provider repeat plan is rejected rather than executed
browser retains exactly one final Assistant message
```

The runner prints `OBSERVED_OK_NOT_AUTOMATIC_PASS`. It never prints raw provider payloads, hidden reasoning, credentials or the full final answer.

A provider failure after verification must remain `effect_state=confirmed`; it must never make the completed business effect eligible for blind replay.

## 6. Failure handling

If any gate fails:

- diagnose the real root cause;
- repair the smallest responsible P5.5/runtime/harness layer;
- do not weaken a product assertion to obtain green output;
- rerun every affected earlier gate after a production/runtime repair;
- continue through the rest of the batch in the same run once repaired;
- do not start P5.6 while any P5.5 HARD gate remains unresolved.

A harness/environment failure may be repaired without rerunning unrelated product gates only when the tested production SHA and causal assertions are unchanged.

## 7. Exit

P5.5 becomes `COMPLETE` only when one coherent lineage has accepted:

```text
P5.5-ODOO-POST-EFFECT          PASS
P5.5-DETERMINISTIC-REGRESSION PASS
P5.5-FULL-ADDON-REGRESSION    PASS
P5-REAL-POST-EFFECT            PASS after evidence review
```

Record exact tested SHA, actual test totals, Odoo/Python/PostgreSQL versions and Codex/Node/Playwright/Chromium versions. Do not store credentials, raw prompts/answers, provider internals, policy payloads or customer data.

After all four pass, mark P5.5 `COMPLETE` and continue directly into P5.6 rather than creating another administrative micro-slice.
