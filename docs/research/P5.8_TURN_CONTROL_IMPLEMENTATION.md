# P5.8 interactive turn control and verified compensation

Date: 2026-08-30  
State: `REAL_ENV_VALIDATION_REQUIRED`  
Validation runbook: `P5.8_VALIDATION_RUNBOOK.md`  
Codex test handoff: `P5.8_CODEX_TEST_HANDOFF.md`

## Outcome

This extension adds modern current-turn controls without changing Odoo authority.

```text
browser composer
    |-- active + empty -> Stop
    |-- active + text  -> durable correction on same turn
    |-- approval + text -> reject old plan + durable correction on same turn
    v
Odoo durable control state
    |-- odoo.ai.turn.control: cancel/applied sequence + legacy migration compatibility
    |-- odoo.ai.turn.intervention: ordered bounded correction rows
    v
host-owned agent loop
    |-- best-effort live Codex turn/steer when current subturn is steerable
    |-- otherwise interrupt/restart disposable provider subturn from durable Odoo state
    |-- reject stale decisions before the write barrier
    |-- serialize final control check against barrier commit
    `-- keep business authority in CapabilityExecutor / policy / verification
```

`odoo.ai.turn.intervention` deliberately uses copied integer/UUID ownership bindings instead of a foreign key to the worker-owned turn row. A running worker may hold the turn row for business work; a browser correction must become durable without waiting on that row lock. Every host read revalidates turn/conversation/user/company binding.

The older bounded `odoo.ai.turn.control.intervention_payload` remains only as compatibility input for previously persisted P5.8 development rows; new corrections are written as dedicated intervention rows and snapshots merge both representations deterministically.

## Stop semantics

Stop is scoped to the active conversation/turn in the browser and never broadcasts to other chat scopes.

The durable Odoo cancel flag remains authoritative. While a Codex subturn is alive, `InteractiveCodexDecisionEngine` polls control state at a bounded interval and sends best-effort `turn/interrupt` to that exact ephemeral `(threadId, turnId)`. If the provider process disappears, Odoo cancellation still survives.

Already streamed answer text is retained and presented with `— Interrumpido`. A queued turn can still be cancelled without starting Codex.

If Stop arrives after the durable write barrier won the final effect boundary, it does not claim that the already verified business effect disappeared. It can stop remaining work; performed effects remain visible and safe compensation is offered only when the host has an explicit inverse.

## Intervention semantics

Corrections are ordered, bounded and persisted as normal user messages plus durable `odoo.ai.turn.intervention` rows on the same Odoo turn UUID.

Each intervention has:

```text
sequence
client_intervention_id
message
message_ref_id
pending | applied | superseded
copied turn/conversation/user/company binding
```

The current limits are strict: at most 16 interventions and a bounded aggregate payload. Reusing a `client_intervention_id` with the same content is idempotent and does not create another row/message; reusing it with different content fails closed.

Queued corrections are included before the first provider decision.

For a running provider decision:

```text
persist in Odoo first
 -> if current App Server turn is alive:
      turn/steer(threadId, expectedTurnId, correction input)
 -> if steer is unsupported/rejected/mismatched:
      turn/interrupt current disposable subturn
      restart NextDecision from Odoo durable intervention list
```

The model sees interventions as untrusted user data. The durable rows are not rewritten into the private working transcript merely to emulate provider state.

After provider completion the host rechecks the latest intervention sequence. A correction that arrived after the last accepted steer invalidates the provider decision and causes a bounded restart. The applied sequence is recorded only for a current decision.

At `awaiting_confirmation`, a new instruction records `approval.rejected`, clears the executable old plan/result/working state and requeues/resumes the same turn. The old plan cannot later execute.

## Final control/effect serialization

The final intervention/Stop versus effect race uses one narrow PostgreSQL transaction-scoped advisory lock derived from the persisted turn UUID.

Both browser control writes and the host's final pre-effect boundary acquire the same lock. The host re-reads durable control state while holding it and commits the existing P5.5 write barrier before release.

Legal outcomes:

```text
control wins
    -> host observes cancellation/new intervention
    -> stale plan cannot cross the barrier

barrier wins
    -> effect may execute
    -> later correction fails with turn_effect_already_committed
    -> Stop affects remaining work only
```

The lock is not held across provider reasoning, capability execution, verification or post-effect synthesis. It grants no business authority.

## Verified compensation instead of fake rollback

Completed effects advertise automatic reversion only when an installed HOST-only compensator exists for the exact capability/version. Compensation is never model-controlled and is not a PostgreSQL rollback.

Initial explicit pairs are:

```text
odoo.record.patch       -> odoo.record.patch.revert
odoo.record.archive     -> odoo.record.archive.revert
odoo.record.unarchive   -> odoo.record.unarchive.revert
```

Compensators are absent from the model catalog. They run through `CapabilityExecutor` under the current effective user. The original preview stores only bounded prior values/state needed for the inverse.

Before compensation the host re-checks current access and verifies the record still equals the verified post-effect state. Later edits cause `capability_compensation_precondition_changed` instead of being overwritten. The inverse write is re-read and must verify before reversion is recorded as completed.

Create/delete and business actions without a guaranteed inverse remain not automatically reversible.

## Browser UX

The composer remains editable during ordinary reasoning. The primary action is:

```text
idle + empty          -> disabled
idle + text           -> Enviar mensaje
active + empty        -> Detener respuesta
active + text         -> Corregir instrucción
approval + text       -> Corregir instrucción
```

The Stop button has a square icon and title/aria-label `Detener respuesta`. A correction draft is cleared only after a valid Odoo acknowledgment.

A completed effect renders `Cambios realizados`. When the host declares compensation available, the UI offers `Revertir cambios`, asks for explicit confirmation and changes to `Cambios revertidos` only after verified success.

## Preserved invariants

- Odoo remains persistence and operational authority.
- Business effects and compensation use the effective user with `su=False`.
- Provider steer/interrupt is transport control only; durable correction state is Odoo-owned.
- Browser never receives provider thread/turn IDs.
- Intervention text is user data, never authority.
- Stale provider decisions cannot cross the write barrier after a newer accepted correction.
- The advisory lock is a narrow ordering mechanism, not execution authority.
- No generic rollback, SQL capability, Python, shell, sudo or arbitrary ORM method is introduced.
- P5.8 remains `REAL_ENV_VALIDATION_REQUIRED`; Phase 6 does not start from implementation alone.
