# P5.8 interactive turn control and verified compensation

Date: 2026-08-30  
State: `REAL_ENV_VALIDATION_REQUIRED`  
Validation runbook: `P5.8_VALIDATION_RUNBOOK.md`

## Outcome

This extension adds modern current-turn controls without changing the accepted Odoo authority model.

```text
browser composer
    |-- empty while active -> Stop
    |-- text while active  -> redirect same turn
    |-- text at approval   -> supersede proposal + redirect same turn
    v
independent Odoo turn-control row
    |-- cancel flag
    |-- ordered user interventions
    |-- provider-applied sequence
    v
host-owned agent loop
    |-- interrupt disposable Codex sub-turn when control changes
    |-- replay ordered redirects as untrusted user data
    |-- reject stale decisions before the write barrier
    `-- keep business authority in CapabilityExecutor / policy / verification
```

The control row deliberately has no FK to `odoo.ai.turn`. A running worker can hold the turn row for business work; Stop/redirect therefore must not wait on that lock merely to signal intent. Binding is copied and revalidated against turn UUID, user and turn id on host reads.

## Stop semantics

Stop is scoped to the active conversation/turn in the browser. It never broadcasts to other chat scopes.

While Codex is running, the interactive adapter polls the Odoo-owned control state at a short bounded interval. A stop request sends best-effort `turn/interrupt` to the current ephemeral Codex provider turn and also remains durable in Odoo. The queue treats that durable control as cancellation authority even if the provider process disappears or the worker later becomes stale.

Already streamed answer text is retained and presented with `— Interrumpido`. The terminal Assistant message is persisted when the worker regains ownership of the turn row. A queued turn can still be cancelled immediately without launching Codex.

## Redirect semantics

Redirects are ordered, bounded and persisted as normal user messages plus private control metadata. They stay on the same Odoo turn UUID.

If Codex is currently deciding, a newer redirect interrupts only that provider sub-turn. The next ephemeral decision receives the full ordered intervention list as untrusted data. If a redirect arrives at the provider terminal boundary, the stale decision is discarded and restarted.

The provider-applied sequence is recorded separately. The host checks it again after reasoning, after plan preparation and immediately before the write barrier. A newer redirect therefore cannot silently allow an older plan to execute. A rare late redirect that races outside the provider wait causes a bounded same-turn requeue with the stale private transcript reset before fresh reasoning.

At `awaiting_confirmation`, writing a new instruction explicitly supersedes the pending proposal, clears its executable turn state, retains the visible historical messages, and requeues the same turn for fresh reasoning. No approve/reject click is required first.

## Verified compensation instead of fake database rollback

Completed effects can advertise automatic reversion only when an installed host-only compensator exists for the exact capability/version. Compensation is not a PostgreSQL transaction rollback and is never model-controlled.

Initial safe compensators are:

```text
odoo.record.patch   -> odoo.record.patch.revert
odoo.record.archive -> odoo.record.archive.revert
```

The compensators are `HOST` exposure capabilities, so they are absent from the model catalog. They run through the existing `CapabilityExecutor` under the effective user and re-check current state before writing. Patch reversion requires the record still to equal the verified post-action values; archive reversion requires the record still to be in the state produced by the original archive. If later edits changed the record, reversion fails closed instead of overwriting them.

Capabilities without a guaranteed inverse, including create/delete and business actions whose inverse may not undo module side effects, are shown as not automatically reversible until a dedicated safe compensator is implemented.

## Browser UX

The composer remains editable while a turn is active. Its primary button resolves to:

```text
active + empty draft -> Stop
active + text        -> Send correction
approval + text      -> Send correction
idle + text          -> Send
```

A completed effect renders a compact `Cambios realizados` summary. When host metadata declares compensation available it includes `Revertir cambios`; after success it changes to `Cambios revertidos`. Unsupported compensation is explained without technical rollback terminology.

## Coverage added

Prepared deterministic coverage includes:

- composer Stop/redirect/send modes;
- same-turn response binding;
- ordered durable redirects and provider applied-sequence tracking;
- pending-approval supersession on the same turn;
- current-chat cancellation isolation;
- interrupted partial-answer retention;
- host-only compensation visibility;
- verified patch compensation;
- conflict-safe refusal after later record changes.

Real gates `P5-REAL-TURN-STOP-REDIRECT` and `P5-REAL-TURN-REVERSION` are added to `P5.8_VALIDATION_RUNBOOK.md`. These tests/gates are not considered passed until executed in the required Odoo/Codex/browser environment.

## Preserved invariants

- Odoo remains persistence and operational authority.
- Business effects and compensations use the effective user with `su=False`.
- Provider interrupts/restarts do not grant provider-side tools or write authority.
- Redirect text is user data, never authority.
- Stale provider decisions cannot cross the write barrier after a newer redirect.
- No generic rollback, SQL, Python, shell, sudo or arbitrary ORM method is introduced.
- P5.8 remains `REAL_ENV_VALIDATION_REQUIRED`; Phase 6 does not start from this implementation alone.
