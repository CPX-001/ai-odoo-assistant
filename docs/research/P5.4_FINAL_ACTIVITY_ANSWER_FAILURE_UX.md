# P5.4 final activity / answer / failure UX

Date: 2026-08-29  
Status: `COMPLETE`
Inspected baseline: `49c77743f05b9ffd745e1ef56c227fc49d6b3217`
Accepted validation/harness checkpoint: `3e2b38d68fe172cd2cf92d7794159f73476ac23d`

## Objective

Close the final browser-presentation contract before post-effect reasoning. P5.4 does not add another runtime, event bus or message store. It tightens the existing P2-P4 presentation layers on top of the accepted P5.1 conversation scopes and P5.2/P5.3 turn semantics.

The playbook requirements are:

```text
user message visible immediately
public activity separate from Assistant prose
answer deltas separate from activity
no duplicate final answer
approval/failure/recovery explicit
streams/events never cross conversation/turn boundaries
no fake Pensando bubble when real public activity is available
```

## Reused infrastructure

P5.4 deliberately reuses:

- P2 `FailureEnvelope` and existing retry/recovery presentation;
- P3 closed public-activity projection and live cursor;
- P4 provisional `answer.delta` channel plus authoritative final answer;
- P5.1 per-conversation turn scopes, which already prevent cross-chat live state leakage;
- P5.3 immutable per-turn settings, which remain unrelated to browser presentation authority.

No new backend authority or persistence model is introduced.

## Implementation

### Final-answer reconciliation

`assistant_final_ux_contract.js` defines an idempotent browser contract for one authoritative final Assistant message per turn. Provisional deltas remain outside the durable/local message list. If the same final turn is projected more than once, the local `local-assistant-<turn>` message is reconciled rather than appended again.

`zzzz_assistant_final_ux_service.js` runs after the accepted P5.1 scoped service and reconciles every conversation scope after submit completion. If the active scope changed, it reprojects only that active scope. Background scopes remain isolated.

### Final presentation

`zzzz_assistant_final_ux.xml` keeps three channels visually distinct:

```text
public activity      -> activity/status section
provisional answer   -> Assistant answer bubble
terminal failure     -> explicit failure alert
```

The generic no-evidence fallback is now a neutral `Preparando respuesta…` status row rather than an Assistant prose bubble. When real public activity exists, that fallback is absent. Settled activity remains inspectable after completion without retaining a spinning in-progress icon.

Action failure is also rendered as an explicit execution-failure alert. Existing approval and recovery sections remain the authority for those states.

### Model-scoped batch receipts

Completed batch mutations have one verified model target but multiple record IDs, so their bounded
browser receipt intentionally carries `record_model` with a null singular `record_id`. The frontend
validator accepts this model-scoped aggregate form. This prevents a successfully executed batch
from being shown as `invalid_response` until history is reloaded.

## Invariants

- Browser presentation cannot authorize, execute or retry an effect.
- The final validated turn response remains authoritative over provisional deltas.
- Public activity never becomes Assistant prose or private reasoning.
- Failure/recovery state remains structured and bounded.
- P5.1 conversation ownership remains the isolation boundary; P5.4 does not introduce global turn state.
- No P5.5 post-effect provider continuation is implemented here.

## Deterministic coverage added

`assistant_final_ux_contract.test.js` covers:

- duplicate local final messages collapse to one authoritative answer;
- final reconciliation is idempotent;
- real activity suppresses the generic waiting fallback;
- activity and answer deltas can coexist as separate channels;
- approval/failure/recovery remain explicit product states.
- verified model-scoped batch receipts remain valid in the live response path.

## Real product-path harness

`tests/e2e/p5_4_final_ux_browser.mjs` prepares `P5-REAL-CHAT-BASIC`. It verifies on real Chromium/Odoo/Codex that:

- the user message is visible before enqueue completes;
- real activity is rendered outside Assistant message bubbles;
- `Pensando…` is not shown while real activity exists;
- after terminal completion there is exactly one Assistant final message;
- activity settles separately from the final answer.

`tests/e2e/p5_4_approval_browser.mjs` reproducibly exercises a current embedded-runtime
`odoo.record.patch` proposal against a disposable partner. It verifies the dedicated approval state,
visible step/capability/risk details, stable turn binding across a preference change, no
pre-approval write and both reject/approve decision paths with fixture restoration.

The machine-readable gate record is `tests/e2e/p5_4_real_gates.json`.
