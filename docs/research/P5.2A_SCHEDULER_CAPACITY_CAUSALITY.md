## Objective

Turn the previous two-cron implementation detail into the first explicit P5.2 host scheduling contract without changing provider/business authority:

```text
bounded installation capacity
+ race-safe claim admission
+ one active causal turn per conversation
```

## P5.2a implementation

`addons/odoo_ai_assistant/models/turn_scheduler.py` became the final Odoo model overlay for `_cron_run_turn_slot()` and reuses the existing queue execution, structured failure, lease and recovery primitives.

The claim decision uses a short transaction-scoped PostgreSQL advisory lock. Only admission and the queued -> running transition are serialized; provider/business execution starts after commit and never holds the scheduler lock.

Subsequent P5.2 concurrency review added one important refinement to the same claim contract: the tiny scheduler claim transaction switches to PostgreSQL `READ COMMITTED` before acquiring the advisory lock. Odoo's normal cursor isolation is `REPEATABLE READ`; without the local isolation change, a worker waiting on the advisory lock could retain a stale transaction snapshot and still observe capacity from before the previous claim committed.

The physical runner pool remains two `ir.cron` records. Administrator configuration exposes `odoo_ai_assistant.concurrent_turns` with a supported range of 1..2. Runtime resolution also clamps direct/invalid parameter edits to a safe value.

Capacity accounting treats these states as consuming execution capacity:

```text
running
cancel_requested
```

`awaiting_confirmation` releases worker capacity but remains a causal blocker for later turns in the same conversation.

Conversation ordering is based on predecessor turn identity (`id`), not `queued_at`. Retry/requeue may update an older turn's queue timestamp; that must not let a later message overtake it.

Terminal states including `completed`, `failed`, `cancelled` and `recovery_required` do not consume capacity or block a later conversation turn. `recovery_required` remains non-replayable under the existing write-barrier contract.

## Preserved invariants

- Odoo remains persistence and scheduling authority.
- Business execution still reconstructs the originating user Environment with `su=False`.
- Existing lease ownership, bounded attempts, cancellation and stale recovery remain authoritative.
- Structured provider failures still flow through `turn_failure` persistence.
- The final registered cron method is explicitly covered so the P5.2 scheduler overlay cannot silently lose to an earlier model extension.
- No arbitrary SQL/tool authority is exposed to the model; PostgreSQL coordination is internal host scheduling only.
- Excess work remains durably `queued`; capacity exhaustion is not a turn failure.

## Focused deterministic coverage authored

`addons/odoo_ai_assistant/tests/test_turn_scheduler.py` covers:

```text
registered cron method -> P5.2 scheduler overlay
capacity=1 + simultaneous claims -> exactly one running
one queued turn + two simultaneous workers -> no double claim
capacity=2 + independent conversations -> both can run
same conversation -> predecessor cannot be overtaken after queued_at changes
awaiting_confirmation -> blocks same conversation but frees global worker capacity
invalid/direct capacity configuration -> safely bounded to 1..2
```

The concurrency cases use independent cursors/threads so a naive `COUNT(running) < limit` implementation would be exposed as a race.

P5.2b adds its own fairness/wake-up suite in `test_turn_scheduler_fairness.py`.
