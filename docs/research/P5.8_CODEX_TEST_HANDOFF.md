## Interactive control observations

For `P5-REAL-TURN-STOP-REDIRECT` verify all of the following on real turns:

- empty composer during active work exposes Stop;
- text during active work sends a correction to the same Odoo turn UUID;
- at least two redirects are applied in order;
- redirect during `awaiting_confirmation` supersedes the old proposal and reuses the same turn UUID;
- Stop affects only the active chat while another chat can continue;
- visible partial answer is retained as interrupted output;
- raw/private reasoning never appears in browser state.

## Effect-boundary race test

For `P5-REAL-TURN-EFFECT-BOUNDARY-RACE`, use a disposable record and a reversible patch/archive action. Repeatedly race a browser redirect or Stop against the instant an authorized plan reaches the first effect boundary. Prefer at least 20 iterations, split across redirect and Stop.

There are only two valid winner classes:

```text
CONTROL FIRST
- redirect/Stop is durably accepted before the barrier;
- the stale pre-control plan does not execute;
- redirect causes bounded same-turn re-reasoning when applicable.

BARRIER FIRST
- the write barrier commits first;
- the effect may execute normally;
- redirect is rejected with turn_effect_already_committed;
- Stop may halt only remaining post-effect synthesis;
- completed reversible effects still expose host-owned reversion.
```

Hard failure conditions:

```text
accepted redirect + stale old effect executes
deadlock or long lock retention across provider reasoning/business execution
duplicate redirect sequence
control leaking into another turn/chat
write occurring without the normal policy/approval/verification lifecycle
```

The advisory lock is intentionally transaction-scoped and narrow. Confirm from timings/log-safe observations that it serializes only the final control check against barrier commit.
