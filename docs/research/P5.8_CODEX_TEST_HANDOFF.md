## 1. Repair the semantic work-item gap first

The following normal-mode shape is a **known failure**, not an acceptable P5.8 result:

```text
Procesando petición
Analizando petición
Inspect Odoo write schema · sale.order
Inspect Odoo write schema · sale.order
Inspect Odoo query schema · res.partner
Inspect Odoo query schema · res.partner
Query Odoo records · res.partner
Query Odoo records · res.partner
Respuesta preparada
Mutate multiple Odoo records · sale.order
Mutate multiple Odoo records · sale.order
Mutate multiple Odoo records · sale.order
Ejecutando acción autorizada
Mutate multiple Odoo records · sale.order
La petición requiere revisión
```

Normal mode must present a small number of coherent host-grounded work items. For a scenario such as `¿puedes crear 200 presupuestos demo?`, the product should be able to express an equivalent semantic shape such as:

```text
Analizando la petición
Preparando 200 presupuestos demo
  Consultando clientes existentes
Creando presupuestos
  50 / 200
  100 / 200
  150 / 200
  200 / 200
Verificando resultados
  200 presupuestos creados
```

Do not hard-code that exact scenario or invent progress. Counts/progress/result summaries are shown only when grounded in validated host facts.

Implement the simplest coherent extension of the existing P3/P5.8 infrastructure that satisfies the target. Reuse `PublicTurnEvent`, `activity_id`, capability metadata/results and the current semantic reducer. Do not create another tool registry or independent runtime.

A suitable design may use, where useful:

```text
parent_activity_id or another host-owned semantic_group_key
category / operation
headline_code + bounded headline_args
status
progress {current,total} when known
result_summary when host-known/verified
references[]
```

Equivalent simpler contracts are allowed after inspecting current code. Requirements:

- lifecycle start/update/completion for one operation becomes one visible item;
- related child operations group only through explicit host-owned semantic correlation, never label equality;
- independent same-capability calls remain distinct unless explicitly grouped;
- normal mode uses human/business semantics and does not expose raw `CapabilityDefinition.title` as the primary row;
- diagnostic mode may show capability/model identifiers and lifecycle detail;
- deterministic UI wording uses semantic codes + bounded arguments + Odoo translation;
- provider readable summaries remain advisory; raw/private reasoning remains excluded;
- progress/result counts must be host-grounded;
- approval/failure/partial/cancelled states remain visible and first-class;
- existing navigation references, Stop/interventions, compensation and write-barrier authority must not regress.

Add deterministic/Odoo/HOOT coverage that would fail on the technical lifecycle dump above. In particular assert that normal mode does not primarily expose titles such as:

```text
Inspect Odoo write schema
Inspect Odoo query schema
Query Odoo records
Mutate multiple Odoo records
```

Do not solve this by simply hiding every capability row. The UI still has to communicate meaningful current work.
